# 数字FAFU 晚查寝自动签到

面向福建农林大学「数字FAFU」App 的晚查寝签到自动化模块，支持 **KernelSU** 与 **Magisk**。

安装后全自动运行：白天静默保活、晚上定时签到，全程无感知。

## ✨ 功能特性

- **自动签到**：在你设的轮询范围（默认 20:00 ~ 23:59）内每分钟查看任务，进入服务端的签到窗口就自动提交，签完即止
- **补签兜底**：主窗口未成功时继续在服务端的补签时段内重试，最大限度避免漏签
- **静默保活**：07:00 ~ 21:25 每 15 分钟轻量调用一次接口，保持登录状态不过期；每次结果都更新统计（`status` 可查看今日成功/失败数），失败还会写进日志（逐次心跳在调试档里看）
- **静默刷新**：登录状态失效时自动在后台刷新，熄屏状态下屏幕不亮起、也不唤醒（打卡页本身仍会短暂打开一次）
- **通知提醒**：签到成功、补签成功、检测到已签到 / 已请假、首次签到失败、首次获取任务失败时弹出通知；三个截止时点（主窗口截止前 30 分钟、主窗口截止、补签截止）若尚未签到会提醒你手动补救；到最晚查看时刻仍未取得任务时也会提醒一条
- **配置页（KernelSU）**：从模块卡片打开，改配置不用 root、不用记路径、不用懂 shell；也能直接手改配置文件（Magisk 使用者走这条）
- **无感运行**：全程后台、不残留任务、不打断使用——只有刷新登录状态时会打开一次打卡页（页面必然进前台，拿不到 token 时还会唤醒屏幕兜底），拿到新 token 后立刻关闭，正常只出现几秒；清理不彻底时让它留在后台，不会把你切到桌面
- **操作按钮**：点击模块「操作」按钮，一键启用 / 停用服务（即时生效，无需重启）
- **动态描述**：模块描述显示开关状态与签到日期时间（例如 `🟢 已启用 · ✅ 09-14 已签到 21:30`），采用绝对日期，即使服务异常退出也能从日期判断信息时效
- **双平台**：KernelSU / Magisk 通用；配置页只在 KernelSU 上出现（Magisk 没有对应机制）

## 📦 安装

1. 获取模块包（二选一）：
   - 下载 Release 中的 `fafu-checkin-*.zip`
   - 自行打包：`sh build.sh`（生成到 `dist/`）
2. 打开 KernelSU / Magisk 管理器 → 模块 → 从本地安装 → 选择 zip
3. 重启手机

## 🔄 更新

模块内置更新检测（`updateJson`），管理器会定期检查新版本：

- **KernelSU**：模块页会显示更新提示，点击即可更新
- **Magisk**：模块页出现「更新」按钮，一键完成

更新源：仓库根目录的 [`update.json`](update.json)（指向最新 Release）。

> **它是唯一打开「有更新」提示的开关**：两个管理器都只比对这里的 `versionCode`
> （大于本机已装的版本才提示），`module.prop` 只被本机读取、仓库里那份不会被拉取。
> 因此**必须先有 Release 与它的 zip，再同步这个文件**——顺序反了，用户点更新只会拿到 404。
>
> **发布新版本时**需更新 `update.json` 的 `version` / `versionCode` / `zipUrl` 三项
> （可用 `scripts/sync_update_json.py` 生成，见「开发与发布」）；
> `changelog` 固定指向本仓库 `CHANGELOG.md` 的 raw 地址（管理器按 Markdown 渲染），无需随版本改动。
>
> 注意：`changelog` 不能填 GitHub Release 网页地址（那是 HTML 页面，管理器会把它当纯文本渲染，
> 显示成一堆 HTML 源码）；请始终使用 raw 文件地址。

## 🎛️ 操作按钮（服务开关）

点击模块的「操作」按钮即可切换服务开关：

- **🟢 已启用** → 点击后停用：停止后台服务，不再进行任何网络请求
- **⏸ 已停用** → 点击后启用：恢复后台服务与自动签到

模块描述会动态显示当前状态与签到信息（日期均为绝对日期）：

| 描述示例 | 含义 |
|----------|------|
| `🟢 已启用 · ⏳ 09-14 未签到` | 服务运行中，09-14 尚未签到 |
| `🟢 已启用 · ✅ 09-14 已签到 21:30` | 09-14 已签到（含签到时间） |
| `🟢 已启用 · 🏖 09-14 已请假` | 09-14 状态为请假 |
| `⏸ 已停用 · 最近签到 09-13 21:31` | 服务已停用，显示最近一次签到 |
| `⏸ 已停用 · 暂无签到记录` | 服务已停用且无签到记录 |

> 描述在事件发生时自动更新（签到成功、开关切换、服务启动），平时每约 10 分钟自动检查一次；
> 若操作后未立即变化，重新打开模块页或下拉刷新即可。
>
> 描述使用绝对日期（MM-DD）而非“今日”等相对表述：即使守护进程意外退出导致描述停止更新，
> 也能通过日期直观判断信息的时效性，不会产生“今日已签到”之类的误导。
>
> 实现方式：KernelSU 使用官方模块配置 `override.description` 覆盖（不修改模块文件，卸载时自动清除）；
> Magisk 下则直接更新 `module.prop` 描述作为兼容方案。

## 🖥️ 配置页（KernelSU）

KernelSU 使用者可以直接在模块卡片上打开一个配置页，改配置不用 root、不用记路径、不用懂 shell。
页面同时显示运行状态，所以「它今晚到底有没有在干活」也在这里看。

### 怎么打开

1. 打开 **KernelSU 管理器** → 模块页；
2. 在**本模块的卡片**上点「打开」（部分版本是点卡片本身进入）。

入口的出现条件（三者同时满足才显示，缺一个就看不到按钮）：

- 模块内存在 `webroot/` 目录（即模块是带页面打包的版本）；
- 模块**已启用**（没有被停用；注意这与本模块的「服务开关」是两回事）；
- 模块**不是待更新状态**（装完新版本后请重启一次手机，让更新生效）。

> 页面由 KernelSU 管理器自带的 WebView 承载，**不需要联网**（见下面的「离线可用」）。

### 能改什么

主界面四项、高级区两项，共六项：

| 配置项 | 默认 | 在页面上的位置 | 改了会怎样 |
|---|---|---|---|
| **服务开关** | 启用 | 主界面 | 停用后立即停止后台服务、不再发起任何网络请求；启用后恢复自动签到。与操作按钮是同一个开关，两处改任一处，另一处跟着变 |
| **保活开关** | 开 | 主界面 | 关闭后不再在白天保活（白天不会为了刷新登录状态而短暂弹出打卡页），只保留轮询范围内的自动签到 |
| **轮询范围起** | `20:00` | 主界面 | 从这一刻开始去查看今晚的任务。这是「**去查看**」的时段，**不是**签到时段——签到窗口与补签窗口仍由服务端任务数据决定，本模块不会因为这里设得早就提前签到 |
| **轮询范围止** | `23:59` | 主界面 | 最晚查到这一刻；到点仍未签到就停止轮询（避免整夜空跑）。当晚的事一旦办完（已签到 / 已请假 / 已提交成功）也会立刻停 |
| **通知开关** | 开 | 主界面 | 关闭后**零通知**（同时也就不再需要降权调用、不再写通知标记） |
| **预警提前量** | `5` 秒 | 高级 | 屏幕已亮、即将打开打卡页之前先弹一条提醒，并留出这么多秒给你读完。设 `0` 表示不加延时。只在屏幕本来就亮时生效（熄屏路径是静默开页，不打扰你） |
| **通知冷却** | `300` 秒 | 高级 | 同类打扰型通知的最小间隔；调小会更容易被连续提醒，调大则更清静 |

> **轮询范围要覆盖你学校发布今晚任务的时间。** 这是页面上一段常驻说明，也是这一项唯一的设置要领：
> 任务若在你设的范围之后才发布，本模块不会再去看，自动签到就会错过。兜底是——
> 到 `min(轮询范围止, 23:00)` 仍未取得今晚任务时，会给你发一条「今晚任务还没发布」的提醒
> （按「一日一次」去重），你收到后手动打开 App 签一下仍来得及。
> **设窄了的代价因此是「收到提醒、自己补救」，而不是静默漏签。**

### 改完怎么生效

点保存后，页面把改动交给脚本侧的**唯一校验闸门**：

1. 脚本侧逐项校验（时间必须是 `00:00`–`23:59`、轮询范围起必须早于止、数字项必须在合理区间内）；
2. **校验通过才落盘**，然后回读生效值回显到页面上，让你确认「写的」和「生效的」是同一份；
3. 随后**自动重启后台服务**，新值立刻生效——不需要你懂「要重启才生效」，也不需要重启手机。

填了非法值（比如 `25:00` 或字母）会被**当场拒绝**：页面上给出原因，**旧值保持不变**，不会写坏配置。

### 页面还会显示什么

打开页面就能看到一份当前状态的快照：

- 今日签到状态与签到时间（已签到 / 已请假 / 未签到）
- 今日保活的成功与失败次数
- 最近一次保活的时间与结果
- 登录状态**是否有效**
- 模块版本号
- 最近几条日志

它与模块描述会有重合——描述大约每 10 分钟刷新一次，页面是你打开那一刻的快照，两者不一致时以页面为准。

### 页面不显示什么

**登录凭证明文（token）不显示**，只显示它当前是否有效。`status` 命令里的 token 默认也是打码形状
（`2_****a1b2`），只有打开调试日志（`DEBUG=1`）才输出明文——见「日志在哪、怎么读」。

### 离线可用

页面**不含任何外部资源引用**（字体、样式、脚本全部随模块打包），所以**飞行模式下也能打开和改配置**；
配色跟随系统的深色 / 浅色模式自动切换。

### Magisk 使用者：继续手改配置文件

**Magisk 没有 WebUI 机制**，模块卡片上不会出现配置页入口。Magisk 使用者请按下一节的说明手改
`fafu-checkin.conf`，配置项的名字、默认值与语义与页面完全一致（两个平台互斥，本项目不为「共存」写代码）。

### 页面写入与手改的关系

- **是同一处**：页面写的值与手写的值都在模块目录的同一个文件 `fafu-checkin.conf` 里，同一套键名、同一套语义。
  页面只是这个文件的可视化编辑器，不存在「页面的配置」和「文件的配置」两份。
- **页面写入是整份重写**：保存时会用登记表里的键重写整个文件，因此**手写的注释会被去掉**，
  **不在登记表里的键会被去掉**。想长期保留注释或自定义变量，就别用页面保存那一份文件。
- **升级模块不丢配置**：本文件属于使用者，模块升级后配置仍然有效，不需要每次升级重配一遍。
- 想只用命令行也行——手改之后执行 `stop` 再 `start`（或重启手机）即可生效。

## 🚀 使用

安装后自动运行，无需任何操作。

```sh
# 查看日志（位于模块目录内）
cat /data/adb/modules/fafu-checkin/fafu_checkin.log

# 手动命令（需要 root）
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh status    # 查看开关 / 服务 / 保活 / token 状态
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh notify    # 发一条测试通知（确认通知能否送达）
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh keepalive # 手动执行一次保活检查
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh refresh   # 手动刷新 token（测试用）
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh toggle    # 切换服务开关（启用 ⇄ 停用）
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh enable    # 启用服务
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh disable   # 停用服务
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh once      # 立即检查一次（幂等）
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh webstate  # 只读输出运行状态与配置生效值（配置页靠它）
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh start     # 启动服务（若已停用则忽略）
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh stop      # 停止服务（不改变开关状态）
```

改配置也可以走命令行（与配置页同一道校验闸门，非法值一样会被拒绝、旧值不变）：

```sh
# 一次只给要改的键也行；成功时回显全部键的生效值
sh /data/adb/modules/fafu-checkin/fafu_checkin.sh setconfig POLL_START=19:30 POLL_END=23:30
```

> 不加子命令等于 `start`；写错子命令会打印完整的用法（命令集合取自命令表）。
> 除 `start`（它就是不带子命令）之外，全部子命令的清单与说明都在源码 `lib/commands.sh`
> 的命令表里，一眼看全。

### 日志在哪、怎么读

日志就是模块目录里的 `fafu_checkin.log`（`cat /data/adb/modules/fafu-checkin/fafu_checkin.log`，
或用管理器的文件功能打开）。它一行记一件事，形如 `事件名: 键=值 …`。

日志分两档，由 `DEBUG` 配置键决定（配置页「高级」区那个「调试日志」开关）：

- **默认档**（`DEBUG=0`，出厂设置）：**只留结果与原因**。签到与补签的成败、保活结果、
  通知链路的异常、每日一次的任务与时间核对都在，日志因此每天只有十几行，每一行都值得看。
- **调试档**（`DEBUG=1`）：把**完整现场**写回来。多出来的是那些分钟级重复、内容又不变的行——
  每次提交的尝试行（含服务端状态码、完整响应体、响应头与耗时）、每次轮询对签到时段的判定、
  保活心跳、页面收尾检查，以及开机后「应用数据暂不可读」到「已就绪」的等待过程。
  （「任务在今晚变了」那一行两档都有——它本来就只在真的变化时写，是结论不是噪音。）

**两个档位的文案逐字一致**，区别只是那些行可见与不可见——照本节与开发文档去查某一行，
不会因为档位不同而查不到。两档共用同一个写日志出口与同一份行格式，不引入级别前缀或标记。

怎么切到调试档：

- **配置页**：KernelSU 使用者打开配置页 → 「高级」区 → 打开「调试日志」→ 保存。
  保存会自动重启后台服务，档位立刻生效，不必重启手机。运行状态区也会显示「调试日志」当前是开还是关。
- **手改配置文件**：在 `fafu-checkin.conf` 里写 `DEBUG=1`（Magisk 使用者走这条），
  然后 `stop` 再 `start`；详见下面的「配置（可选）」。

默认档下每次保活**不再各写一行**（成功时那行心跳已被降级；今日成功 / 失败次数与最近一次结果看
运行状态或 `status` 命令即可）。而**签到与保活失败仍会记，原因一变就再记一条**——同一晚不再被
同一条重复原因刷屏，但也不会漏掉新情况。

**token 在默认档里是打码的**：无论出现在日志还是 `status` 命令的输出里，一律是
`2_****a1b2` 这个形状——保留 `2_` 前缀与**尾 4 位**，所以仍然看得出「换没换」（打码前后不一致
就是换过）。短得不足以保留尾 4 位时整串打码。打开调试档才输出明文，那时是你自己在排障。
授权头本来就不进日志（响应头白名单里没有它）。

**把日志贴给别人看之前**：默认档下日志里的 token 已经是打码的，可以直接贴；只在两件事上留心——
① 调试档下 token 是明文，贴之前先把 `2_` 开头的那几串涂掉；② **保活统计文件
`fafu_keepalive.status` 里的 token 字段仍是明文**（它是运行时状态、被当值取用），
别把整个模块目录打成一个包发出去。要连带看这个文件时，把那一格涂掉即可。

日志超过 256KB 会自动保留最近 1000 行；想从干净的一份看起，重刷一次模块即可（等于清空）。
轮转与保留策略不随档位变化，**一直开着调试档也不会无限增长**。

> 每一行该看哪个字段、怎么判断问题出在哪，见开发文档的「排障日志字段对照」一节。

## ⚙️ 配置（可选）

配置文件就是上面那节说的同一个文件：模块目录里的 `fafu-checkin.conf`
（即 `/data/adb/modules/fafu-checkin/fafu-checkin.conf`）。**KernelSU 使用者优先用配置页改**；
Magisk 使用者、以及配置项不在页面上的那两项，在这里手改。文件里的每个键**都可不写**——
不写就是用默认值。

```sh
# 全部配置项与默认值（按需取用，不用的行删掉即可）
KEEPALIVE=1         # 白天保活：1 = 开（默认），0 = 关（仅保留轮询范围内的自动签到）
POLL_START=20:00    # 轮询范围起：从几点开始去查看今晚的任务（默认 20:00）
POLL_END=23:59      # 轮询范围止：最晚查到几点（默认 23:59）
NOTIFY=1            # 通知：1 = 开（默认），0 = 完全关闭（零通知、零降权调用、零标记）
NOTIFY_LEAD=5       # 预警提前量，秒（默认 5；0 = 不加延时；仅屏幕已亮时生效）
NOTIFY_COOLDOWN=300 # 同类打扰型通知的最小间隔，秒（默认 300）
DEBUG=0             # 调试日志：1 = 打开调试档（默认 0 = 关闭，日志只留结果与原因）
KA_START=07:00      # 保活时段起（默认 07:00）——只能手改，不在配置页上
KA_END=21:25        # 保活时段止（默认 21:25，上界不含）——只能手改，不在配置页上
```

逐个键的语义：

| 键 | 默认 | 说明 | 配置页 |
|---|---|---|---|
| `KEEPALIVE` | `1` | 白天保活开关；`0` = 关闭白天保活，只保留轮询范围内的自动签到 | ✅ 可见 |
| `POLL_START` | `20:00` | 轮询范围起：从几点开始去查看今晚的任务。这是「**去查看**」的时段，**不是**签到时段（签到窗口与补签窗口由服务端任务数据决定） | ✅ 可见 |
| `POLL_END` | `23:59` | 轮询范围止：最晚查到几点；到点仍未签到就停止轮询 | ✅ 可见 |
| `NOTIFY` | `1` | 通知开关；`0` = 完全关闭通知（同时也就不再需要降权调用、不再写通知标记） | ✅ 可见 |
| `NOTIFY_LEAD` | `5` | 打开打卡页之前的预警提前量，单位**秒**；`0` = 不加延时；只在屏幕已亮时生效 | ✅ 可见（高级） |
| `NOTIFY_COOLDOWN` | `300` | 同类打扰型通知的最小间隔，单位**秒** | ✅ 可见（高级） |
| `DEBUG` | `0` | 调试日志开关；`1` = 打开调试档（多出提交尝试、时段判定、保活心跳这些逐次现场，**token 输出明文**）；`0` = 默认档，日志只留结果与原因，token 打码。非法值退回默认值 | ✅ 可见（高级） |
| `KA_START` | `07:00` | 保活时段起——配合你的作息调整白天保活的时间范围 | ❌ 仅手改 |
| `KA_END` | `21:25` | 保活时段止（**上界不含**：到点即不再保活，与签到时段留出间隔） | ❌ 仅手改 |

**轮询范围要覆盖你学校发布今晚任务的时间**：范围设窄了、任务发布得更晚时，本模块不会再去看，
自动签到就会错过。兜底是到 `min(POLL_END, 23:00)` 仍未取得今晚任务时给你发一条
「今晚任务还没发布」的提醒（按「一日一次」去重），收到后手动打开 App 签一下仍来得及。

时间项写 `HH:MM`（`00:00`–`23:59`），且**轮询范围起必须早于止**；不支持跨午夜的轮询范围
（例如 `23:00` ~ `01:00`）。

**写坏了怎么办**——两种写法，两种处理：

- **手改文件**：非法值会被**退回该键的默认值**，本模块按默认值继续运行，不会因此改变程序行为
  （配置值永远不会被求值成代码，写错一个字符不会变成"执行了别的什么"）；
- **配置页保存**：更严格——非法值被写入闸门**当场拒绝**、旧值原样保留，并在页面上给出原因。

所以「页面改」与「手改」虽然落在同一个文件上，容错方式并不相同：页面是**拒绝写入**，
手改是**读回时兜底**。改完不确定有没有生效时，用配置页或 `status` 看一眼当前生效值最稳。

修改后执行 `stop` 再 `start` 即可生效（或重启手机）；用配置页保存则自动重启服务，不必手动做这一步。
**`DEBUG` 同样按这条走**：它在守护进程启动时读一次，所以手改配置的人要 `stop` 再 `start`，
在配置页上改的人保存完就已生效。

## ❓ 常见问题

**Q：通知为什么显示成「Shell」？没收到通知怎么办？**

A：这是 Android 的限制——本模块是纯脚本、没有自己的 App，通知只能借系统 shell 的身份发出，
因此在通知栏里归属为 **Shell**，用途是给你留时间手动补救，不代表它来自某个可疑应用。

如果**完全收不到**通知，按顺序排查：

1. 看日志的启动行有没有 `notify=[su - shell -c]`：
   - 显示 `notify=[不可用]` → 通知降权链路不通（`su` 探测失败），通知被静默跳过，签到功能不受影响；
2. 系统设置里检查 **Shell 的通知权限**是否被关闭（部分国产 ROM 默认拦截）；
3. 部分 ROM 会静默丢弃 root 身份发出的通知（命令返回成功但不显示）——模块已固定降权为 shell 身份规避此问题；
4. 熄屏久了系统会进入 Doze，通知可能被延迟投递，**三个截止提醒因此可能晚到**，别把它当精确闹钟。

不需要通知时，在 `fafu-checkin.conf` 里设 `NOTIFY=0` 即可完全关闭（KernelSU 使用者也可以直接在配置页上关）。

**Q：手机锁屏/息屏时能正常工作吗？**

A：可以。熄屏状态下的刷新是静默的（屏幕不亮、不唤醒），实测熄屏下数秒内即可完成刷新。

**Q：如何临时暂停自动签到？**

A：点击模块「操作」按钮即可停用服务（再点一次恢复）；停用期间不会进行任何网络请求。也可以用 `disable` / `enable` 命令。

**Q：停用服务和在管理器里禁用模块有什么区别？**

A：操作按钮是**服务级开关**（即时生效、可随时恢复）；管理器里的禁用是**模块级**操作（需重启生效，且禁用后操作按钮无法执行）。日常暂停建议使用操作按钮。

**Q：会重复签到吗？**

A：不会。每次先查询签到状态，已签到自动跳过。

**Q：白天会不会打扰我？**

A：不会。保活只是轻量接口请求；仅当登录状态失效时才会刷新，且屏幕亮着时会延后：
- 熄屏后自动静默刷新（屏幕不亮、不唤醒，无感知）；
- 若一直亮屏，则留到轮询范围（默认 20:00 起）内一并处理（此时页面短暂出现，你能直观理解是签到引起的）。

**Q：亮屏时保活还工作吗？**

A：工作。保活调用不受屏幕状态影响（每 15 分钟一次）；只有“调用失败后的刷新”会延后到熄屏
或签到时段，避免白天出现无解释的页面弹出。

**Q：怎么确认保活一直在正常工作？**

A：两种方式：
- 运行 `status` 命令，会显示保活状态与具体 token，例如：
  `保活: 最近 2026-10-03 12:15:30 ✅ · 今日 24 成功 / 0 失败`、`token: 有效 2_****a1b2`
  （「最近」那一栏是完整日期时间；若最近一次记录不是今天的，那一行会改成
  `保活: 最近 2026-10-03 12:15:30 ✅（今日暂无记录）`）；
- 查看日志：**保活失败**每次都会记一行（原因变了会再记一条），**保活成功在默认档不再逐次记行**——
  它每 15 分钟一条、内容又不变，成功次数在运行状态里已经有了，没必要刷屏。打开调试日志
  （`DEBUG=1`）就能把逐次心跳看回来：
  - 成功：`保活: ✅ 2_****a1b2 token 有效 (今日 24 成功 / 0 失败)`
  - 刷新：`保活: ✅ 静默刷新成功 2_****a1b2 → 2_****c3d4`
  - 失败：`保活: ❌ 2_****a1b2 调用失败 rc=7 screen=on net rc=7 http=- err=curl: (7) Failed to connect ... 耗时=1175ms (今日 24 成功 / 1 失败) — 屏幕亮着，延后（熄屏或签到时段自动刷新）`
    （`rc=` 是模块观察到的返回码、`screen=` 是当时的屏幕状态，中间那一段是接口层留下的原话；
    紧跟其后的那句是这次采取的动作，也可能是「刷新冷却中，稍后再试」或「尝试静默刷新」）
  两档的文案逐字一致，所以按上面的字段查不会因为档位不同而查不到。

> **日志里「少了一行」不等于服务停了**：默认档省掉的都是分钟级重复的「什么都没发生」的行。
> 判断保活还在不在跑，看 `status` 或配置页运行状态里的「今日成功 / 失败次数」与「最近一次结果」，
> 那里是每次保活都更新的；真要逐次数，就把 `DEBUG` 打开。

日志超过 256KB 会自动轮转（保留最近 1000 行），无需手动清理。

**Q：日志里怎么没有 XXX 了？升级之后少了好多行，是不是坏了？**

A：多半是**默认档把它们收起来了**，不是坏了。默认档只留「结果与原因」，以下几类分钟级重复、
内容又不变的行改在调试档才出现（`DEBUG=1` 打开即可看到，打开前后文案逐字一致）：

| 少掉的行（文案片段） | 它原本多久一条 | 现在改看哪里 |
|---|---|---|
| `[任务名] 不在签到时段` | 窗口内还没到签到时刻时每 60 秒 | 不需要看：没到点本来就无事发生；到点签到后会有结果行 |
| `保活: ✅ … token 有效` | 每 15 分钟 | `status` 或配置页运行状态的「今日成功 / 失败次数」与「最近一次结果」 |
| `页面关闭检查: 残留活动=0` | 每次关页 | 不需要看：正常时恒为 0，**真残留**时那行「页面移除未彻底」仍在默认档 |
| `提交尝试: try=…` | 每次提交 | 提交的**结果**仍在默认档（签到成功 / 补签成功 / 签到失败各一行），失败原因里照样带着接口那次的完整诊断 |
| `应用数据暂不可读` / `应用数据已就绪` | 只在重启后的就绪等待里 | 不需要看：那对瞬间状态；等不到会另有一行「未检测到应用数据」留在默认档 |
| `通知链路: 降权写法 […] 可用` | 每次启动探测 | 启动行的 `notify=[…]` 仍是默认档，一眼看得出降权链路通没通 |
| `保活: ❌ … 调用失败 rc=…`（重复的那些） | 失败时每 15 分钟 | 同一种失败当日只留首次，**原因变了会再留一条**——所以「少了几条」不等于「少了一个问题」；`status` 的今日失败数照旧每次累加 |

另外**升级后请重启一次手机**（或让服务重新启动）：档位在守护进程启动时读一次。若开了调试档
却看不到这些行，先确认配置文件里写的是 `DEBUG=1`（不是 `2` 或其它值），并确认服务已重启。

**Q：怎么看不到 token 了？我的 token 去哪了？**

A：默认档下它变成了 `2_****a1b2` 这种形状——保留了 `2_` 前缀与**尾 4 位**，中间打码。
这么做是因为日志经常要被贴到群里求助，而 `2_` 开头那串就是你的登录凭证：忘了涂掉就等于把它交出去。

- **想确认「token 换没换」**：不必看明文——尾 4 位变了就是换过（例如 `2_****a1b2` → `2_****c3d4`）；
- **想确认「token 还有效吗」**：看 `status` 输出的 `token: 有效 …` / `token: 失效或网络异常 …`，
  或配置页的登录状态一项（那里本来就不显示凭证明文）；
- **排障确实要看明文**：把 `DEBUG` 设成 `1`（配置页「高级」区的「调试日志」，或手改配置文件后
  `stop` 再 `start`），日志与 `status` 就恢复输出明文；用完记得关回去。

**Q：需要手机在签到范围内吗？**

A：本模块适用于不校验位置的签到任务。如学校要求定位，请遵守相关规定。

**Q：日志出现「获取任务失败」怎么办？**

A：多为网络问题，会自动重试；若持续出现，可能是系统接口变更，请提 Issue。

| 文件（模块目录内） | 说明 |
|------|------|

| `fafu-checkin.state` | 服务开关状态 |
| `fafu_checkin.status` | 最近签到记录（用于动态描述） |
| `fafu_keepalive.status` | 保活统计（今日成功/失败次数、最近一次时间；另存一份最近用过的 token，**那份是明文**——它是运行时状态、被当值取用，不受日志档位与打码影响） |
| `.fafu_checkin.pid` | 守护进程 PID |
| `.fafu_checkin_done` | 当日签到完成标记 |
| `.fafu_notify_fail` | 当日「失败类通知」已发标记（避免重试时反复打扰） |
| `.fafu_notify_nosign` | 主窗口截止前 30 分钟的未签提醒已发标记 |
| `.fafu_notify_late` | 主窗口截止（进入补签）提醒已发标记 |
| `.fafu_notify_miss` | 补签截止的最终未签提醒已发标记 |
| `.fafu_notify_last` | 预警通知的冷却基准（防止短时间反复打扰） |
| `.fafu_task_seen` | 当日「已取得任务」标记；它同时是「任务还没发布」那条兜底提醒的已发标记（真的取到任务、或已经为此提醒过，任一成立就不再打扰） |
| `.fafu_task_snap` | 任务快照：判断今晚的任务有没有变化（跨日自动失效） |
| `.fafu_api.err` | 最近一次接口调用的诊断行（状态码 / 正文 / 响应头 / 耗时） |
| `.fafu_api.hdr` | 最近一次接口响应的响应头原文（日志只取其中四项） |
| `.fafu_api.raw` | 网络工具的报错原文（接口调用失败时的原始信息） |

上面这三个 `.fafu_api.*` 是接口层自己管的**旁路文件**，不是日志：`DEBUG` 只作用于
「往 `fafu_checkin.log` 写行」这一处，这三个文件**不受档位影响**——默认档下最后一次调用的
完整事实（状态码 / 正文 / 响应头原文 / 耗时）仍然留在那里，排查时该看还看得见。
`fafu_keepalive.status` 里的 token 明文同理，不受档位与打码影响。

另一个文件不属于运行时状态，而是**使用者自己的配置**：`fafu-checkin.conf`（见上一节）。
它由使用者拥有、由配置层读写。

> 说明：模块更新（重装新版本）会替换模块自身的文件；日志与开关这类运行时文件是否随之重置
> **以真机为准**（本机无法验证管理器的更新行为）。**配置文件按设计保留**——它不在模块包内，
> 卸载脚本之外的任何脚本都不会删除它。想留日志的话，更新前备份一份最稳。

## 🗑️ 卸载

在管理器中卸载模块并重启即可，卸载脚本会自动清理干净：

- 停止后台服务（含进程兜底清理）
- 关闭可能残留的签到页面
- 删除模块运行期间生成的全部文件（均位于模块目录内，随模块目录一并移除）
- 动态描述配置由 KernelSU 在卸载流程中自动清除

无需手动清理任何文件，`/data/adb/` 根目录也不会留下任何残留。

## 🛠️ 开发与发布

### 开发文档

- [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md) — 技术文档：系统知识（签名 / token / 接口）、
  模块架构、调试手册（已知坑）、重新逆向指南、测试方法、维护约定

### 环境要求

推荐 **WSL2（Ubuntu）** / Linux / macOS；Windows 下也可使用 Git Bash（注意换行符与文件权限）。

```sh
# 一次性准备（WSL2 示例）
sudo apt update && sudo apt install -y git zip unzip

# 克隆与构建
git clone https://github.com/Bonger34/fafu-checkin.git
cd fafu-checkin
sh build.sh          # 发布构建 → dist/fafu-checkin-<版本>.zip
sh build.sh dev      # 开发构建 → dist/fafu-checkin-<版本>-dev.<commit>.zip
```

> 提示：仓库已通过 [`.gitattributes`](.gitattributes) 强制 **LF 换行**，请勿改回 CRLF
> （会导致脚本在设备上无法执行）；在 Windows 下打包建议使用 WSL，以保留脚本的可执行权限
> （安装脚本也会自动修正权限，作为兜底）。

### 两种构建模式

| 命令 | 产物名 | 用途 |
|---|---|---|
| `sh build.sh` | `fafu-checkin-<版本>.zip` | **发布**（文件名与 `update.json` 的 `zipUrl` 对应） |
| `sh build.sh dev` | `fafu-checkin-<版本>-dev.5c1a6a4.zip` | **日常测试**（带 commit 标识，可追溯） |

CI 的自动构建使用 **dev 模式**：Actions 产物（artifact）名为 `fafu-checkin-dev-<短commit>`，
里面的 zip 仍是 `fafu-checkin-<版本>-dev.<短commit>.zip`，便于在多次 push 之间区分；
dev 版会移除 `module.prop` 的 `updateJson`（不参与管理器更新检测，避免开发版被提示升级到
正式版）；正式发布时使用干净的发布构建产物。

### 安装到设备

```sh
adb push dist/fafu-checkin-*.zip /sdcard/Download/
# 然后在 KernelSU / Magisk 管理器中「从本地安装」
```

或等待 CI 发布后在管理器内直接更新。

### 发布新版本（手动发布）

自动化仅负责**构建**，发布由维护者手动执行（便于检查产物与说明）：

**1. 准备版本**

- 更新 `module.prop`：`version`（如 `v1.1.7`）与 `versionCode`（+1）
- 在 `CHANGELOG.md` 顶部添加对应小节（格式：`## v1.1.7`）——该小节将作为**发布说明**

**2. 提交并推送**

```sh
git commit -am "v1.1.7: ..."
git push
```

推送后 [`.github/workflows/build.yml`](.github/workflows/build.yml) 会自动构建，
产物在 Actions 运行页的 **Artifacts** 中下载（保留 90 天）。

> **此时管理器还不会提示更新**：两个管理器都只按 `update.json` 里的 `versionCode`
> 判定（`module.prop` 只被本机读取，仓库里那份不会被拉取）。真正打开提示的是第 4 步。

**3. 出发布包并创建 Release**

**发布包必须本地用 `sh build.sh` 出**（见「两种构建模式」）：CI 跑的是 dev 模式，
包名与包内版本串都带 `-dev.<短 SHA>` 且移除了 `updateJson`，而发布产物的版本串要与
`module.prop` **逐字一致**（`build.sh` 会硬校验这一条），拿 CI 产物当发布包会在那里失败。

```sh
sh build.sh          # → dist/fafu-checkin-v1.1.7.zip
# tag 先本地建好并推上去：**必须是带注释的**（-a），与历史版本同形，
# 注释就是发布标题——全部 v1.x 版本都这样，别建成轻量 tag
git tag -a v1.1.7 -m "v1.1.7：一句话摘要"
git push origin refs/tags/v1.1.7
gh release create v1.1.7 ./dist/fafu-checkin-v1.1.7.zip \
  --title "v1.1.7：一句话摘要" \
  --notes-file CHANGELOG_SECTION.md    # 内容取自 CHANGELOG 对应小节
```

tag 要打在**步骤 2 那个已通过 CI 的提交**上（`git tag` 不带提交号即取当前 `HEAD`），
这样包与 tag 指向的是同一份代码。

> **两个踩过的坑**：
> ① `gh release create --verify-tag=false` 会**顺手建一个轻量 tag**，把标签约定搞乱
>    （要么别用这个开关，要么像上面那样自己先建带注释的 tag）；
> ② **删掉远端 tag 会让 GitHub 把 Release 转成 draft**（更新源仍在，但管理器看不到更新）。
>    真要重建 tag，删完必须 `gh release edit <tag> --draft=false` 把它发布回来。

**4. 同步 update.json**（这一步才会让管理器开始提示更新）

```sh
python3 scripts/sync_update_json.py v1.1.7 9 \
  "https://github.com/Bonger34/fafu-checkin/releases/download/v1.1.7/fafu-checkin-v1.1.7.zip"
git commit -am "chore(release): 同步 update.json 至 v1.1.7"
git push
```

> **顺序不能颠倒**：`update.json` 的 `versionCode` 一旦大于用户已装版本，提示立刻出现；
> 这一步必须排在 Release 与它的资源**都已经存在**之后，否则用户点更新只会拿到 404。
> 第 3 步在任何顺序下都不会有这个问题。
>
> 也可直接用 GitHub 网页手动编辑 `update.json`（仅需改 `version` / `versionCode` / `zipUrl` 三项）。

**CI 职责划分**

| 工作流 | 触发 | 职责 |
|---|---|---|
| [build.yml](.github/workflows/build.yml) | push main / 手动 | 语法检查 + 元数据校验 + 构建 zip（产物供下载） |
| [check.yml](.github/workflows/check.yml) | PR / 手动 | 语法检查 + 元数据校验（快速反馈） |
