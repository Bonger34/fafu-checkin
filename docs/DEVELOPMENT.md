## 一、系统知识（逆向结论）

### 1.1 目标应用

- **数字FAFU**（`cn.edu.fafu.iportal`）——基于华为 WeLink 的校园 App
- 打卡入口链路：桌面快捷方式「打卡」→ `W3SplashScreenActivity` → 路由分发 → H5 页面
- H5 应用：`http://stuhealth.fafu.edu.cn/declarew/#/fafu/login`
- 接口服务：`http://stuhtapi.fafu.edu.cn/health-api`

### 1.2 认证机制

- 登录态为 **token**，格式 `2_<32位十六进制>`，存于 App 的 WebView localStorage
- 有效期：**滑动过期**——每次调用续期，持续调用下长期有效（2026-09-14 全流程实测：
  同一 token 经 32 次保活连续有效 12 小时以上，签到全程无刷新）；闲置则会失效
  （实测边界：46 分钟仍有效、5.4 小时后已失效；精确阈值未测定。保活间隔 15 分钟，远低于实测下限）
- 获取 / 刷新方式：打开打卡页触发**免密登录**
  （`HWH5.getAuthorizationCode()` → `third_party/welink/login` 换取 token）
- 没有独立的 refresh 接口——刷新只能通过"打开页面"完成

### 1.3 请求签名

所有接口请求需携带 `Authorization` 头，格式：

```
base64( 时间戳:随机数:MD5(密钥 + 签名URL + 时间戳 + 随机数):token )
```

- **密钥**：`AtPs2O1xEnhwkKDV`（从 H5 混淆代码中解出，见 §4）
- **签名 URL**：不含查询串的完整 URL，如
  `http://stuhtapi.fafu.edu.cn/health-api/sign_in/student/my/page`
- 时间戳为秒级；随机数为 16 位字母数字
- 时间戳与北京时间偏差过大会被服务端拒绝（408）

Python 验证片段：

```python
import base64, hashlib, time, random, string
SECRET = "AtPs2O1xEnhwkKDV"
def make_auth(sign_url, token):
    nonce = ''.join(random.choice(string.ascii_letters + string.digits) for _ in range(16))
    ts = int(time.time())
    h = hashlib.md5((SECRET + sign_url + str(ts) + nonce).encode()).hexdigest()
    return base64.b64encode(f"{ts}:{nonce}:{h}:{token}".encode()).decode()
```

### 1.4 关键接口

| 接口 | 方法 | 说明 |
|---|---|---|
| `sign_in/student/my/page` | POST | 查询签到任务（参数 `rows` / `pageNum`） |
| `sign_in/{id}/student/sign` | POST | 提交签到（参数 `lng` / `lat`，本任务不校验位置） |

任务时间字段（毫秒时间戳）：

- `beginTime` ~ `endTime`：主窗口 **21:30 ~ 22:30**
- `supplementEndTime`：补签截止 **23:00**
- `signInStudent.signState`：`0` 未签 / `1` 已签 / `2` 已请假

### 1.5 token 提取（设备端）

token 存放于 App 私有目录的 WebView localStorage（leveldb 格式，UTF-16LE 存储）：

```
/data/data/cn.edu.fafu.iportal/app_webview/Default/Local Storage/leveldb/
```

按文件修改时间排序读取、取最后一个匹配：

```sh
LD="/data/data/cn.edu.fafu.iportal/app_webview/Default/Local Storage/leveldb"
ls -tr "$LD" | while read f; do cat "$LD/$f"; done \
  | tr -d '\000' | grep -o '"token":"2_[0-9A-Fa-f]*"' | tail -1
```

> 需要 root。取最新值即可（每次免密登录会覆盖写入新 token）。

## 二、模块架构

### 2.1 文件职责

运行时的模块是「入口 + 库层目录」的多文件形态：入口只做装配与调度，能力实现按职责分 10 层，
改一个功能只需读一到两层。

**模块内（打进 zip）**

| 文件 | 职责 |
|---|---|
| `fafu_checkin.sh` | 入口：定位模块目录 → 按序加载各层 → 命令分发 → 守护主循环 |
| `lib/base.sh` | 环境与工具：模块/工具链定位、日志与轮转、时间源、原子写、键值读写、JSON 单字段。**统一写日志出口**（`_log_write` / `log` / `logd` / `log_once`）与 **token 打码助手 `tok_mask`**（公开名只此一个）都在本层（见 §2.1.2 base 层） |
| `lib/config.sh` | **配置的唯一归属地**：键登记（键名 / 默认值 / 校验规则）、生效值读数、写入闸门（校验 → 整份原子重写 → 回读回显）。配置文件仍是模块目录里的 `fafu-checkin.conf`，格式与语义不变——本层只是它唯一的读写口。调试档位 `DEBUG` 也是本层的一个在册键：取值 `0` / `1`、默认 `0`、与 `KEEPALIVE` / `NOTIFY` 同一档开关校验；生效值落在同名变量 `DEBUG` 上，base 层的日志出口**直接读那个变量**（不调本层函数，见 §2.1.2 base 层） |
| `lib/state.sh` | 运行时状态的**唯一读写者**：服务开关、签到记录、保活统计、完成标记、五类通知标记（`fail` / `nosign` / `late` / `miss` / `nopub`）、通知冷却基准；对外只给语义函数，文件格式是它的契约。**守护进程存活判据 `daemon_pid`** 也在这里（PID 文件由入口写，判读只此一处） |
| `lib/api.sh` | 接口：token 提取、请求签名、HTTP 调用（含 wget 超时选项探测）；`http_post` 是全程序唯一的网络出口 |
| `lib/device.sh` | 设备控制：屏幕状态、前端任务枚举、打开/移除打卡页 |
| `lib/notify.sh` | 通知：事件名 → tag 与文案、降权探测、发送、每日一次去重、打扰冷却 |
| `lib/desc.sh` | 模块描述：读状态生成描述文本并写入（KernelSU 覆盖优先，回退改写元数据） |
| `lib/keepalive.sh` | 刷新 token 与白天保活：刷新分三段（`refresh_silent` / `refresh_wake` / `refresh_finish`），保活时段 `ka_in_window`、15 分钟节流 `ka_due`、30 分钟冷却、亮屏延后 |
| `lib/signin.sh` | 签到决策：取任务 / 解析字段 / 判定该做什么 / 提交并记录（三档返回码） |
| `lib/commands.sh` | 11 个子命令与它们的**命令表**：表同时驱动子命令分发、需要降权探测的集合与用法文本（`start` 例外，见 §2.2 的守护循环） |
| `webroot/` | KernelSU WebUI 配置页：入口 `index.html`（`webroot/index.html`），样式与脚本全在本地、零外部资源引用；页面只经命令层调脚本，不自己读写任何文件 |
| `service.sh` | 开机启动（等 `sys.boot_completed` 后拉起守护；已停用则跳过） |
| `action.sh` | 操作按钮 → 切换服务开关 |
| `customize.sh` | 安装脚本（脚本 0755；库层按只读数据文件 0644） |
| `uninstall.sh` | 卸载：停进程 / 关页面 / 清理运行时文件 |
| `update.json` | 更新检测源（`module.prop` 的 `updateJson` 指向它） |

**只在仓库里（不打进 zip）**

| 文件 | 职责 |
|---|---|
| `build.sh` | 打包：清单含 `lib/`，打完后逐个核对产物，缺文件即构建失败 |
| `tools/run-tests.sh` · `tests/` | 断言总入口与用例（§5.1） |
| `tools/check-layer-order.sh` · `tools/layer-whitelist.txt` | 层序守卫与它的动态分派白名单 |
| `tools/lib.sh` | 共用小函数：busybox 定位、层清单读取（`read_layers`） |
| `tools/device-smoke.sh` | 设备冒烟：装一次后自动走完手动命令并核对启动行 / 描述 / 保活节拍，证据落盘（§5.4）。只经 `fafu_checkin.sh <子命令>` 与模块日志观察模块，**不自己读运行时状态文件** |
| `tools/diag-time.sh` · `tools/diag-net.sh` | 设备取证脚本（只读，不改模块、不发签到）：前者比对设备时区 / 服务端 `signTime` / 模块记录，判定描述里的签到钟点为何偏差；后者探明本机 wget 与 curl 在 HTTP 错误时各拿到什么（选 curl 的依据即来自它） |

**层结构的约定**（这几条是结构不变量，改结构时先读这里）：

- **注释口径（第二版）**：文件头只留「层名 —— 职责 / 加载顺序 / 配置与注入点」（≤15 行），
  **不写指向模块外的指针**，也**不再维护「对外提供：…」清单**（那份清单已经漏过三处，
  且没有任何判据能验证它列全；对外函数名以本节的层清单与各层实现为准）。文件内任何连续注释块
  **≤3 行**，只留三类内容：用法与配置、一行「改这里会坏什么」的不变量、非直觉技巧的解释；
  否决方案与实测历史的完整版本在 §2.1.2，代码里只留结论。这条口径由 `tests/headers.sh` 守着
  （它用反向样本自证判据真的会失败），改注释时会一起报红。判据的完整说明与
  「守卫管不了什么」见 §5.1 的 `tests/headers.sh` 那一条。
- **加载顺序**（入口 `fafu_checkin.sh` 里的 `FAFU_LAYERS`，唯一真源）：
  `base → config → state → api → device → notify → desc → keepalive → signin → commands`。顺序即依赖方向：
  **一层只能引用更早加载的层**，由 `tools/check-layer-order.sh` 守着（注释里提到更后层的名字不算引用）；
  断言（`tests/harness.sh`）与打包（`build.sh`）也从入口读这份清单，不另存一份。
  注意两处相邻关系：`config` 紧随 `base`、排在 `state` 与 `notify` 之前（它只用 base 层的原语）；
  而 `keepalive` 必须早于 `signin`——签到决策会调用刷新流程。
- **配置只归 config 层**：模块目录里的 `fafu-checkin.conf` 只有 `lib/config.sh` 读写，其余层与入口
  **一律经它的读取函数取值，不再各自写 `${VAR:-默认}` 兜默认值**（保活层与通知层原先自带的那两处
  默认值定义已迁进本层）。这样「一个键的默认值 / 取值范围 / 校验规则」只有一处定义，
  页面、写着闸门与运行时看到的是同一份语义。本层对外两块能力：
  - **生效值读数**：各层按需取值，拿到的永远是「已代入默认值、已过校验」的值；
  - **写入闸门**（由新增的写入子命令调用，见 §2.2）：全键白名单枚举、逐项校验、非法即拒绝并保留旧值，
    通过才**整份原子重写**配置文件（不保留手写注释、不保留登记表之外的键），最后回读生效值回显。
    它是配置写入的**唯一**入口——页面没有第二条路。
  写错的文件**在读回时兜底**（非法值退回该键的默认值），而经闸门写入时是**拒绝写入**：
  两种容错方式不同，改这里时别把两者混成一条路径。
- **运行时状态只归 state 层**：模块目录里的运行时文件（开关 / 签到记录 / 保活统计 /
  完成标记 / 通知标记 / 冷却基准 / 任务快照）只有 `lib/state.sh` 读写，其余层与入口一律经它的语义函数：
  开关 `svc_is_disabled` / `svc_set`，签到记录 `sign_get` / `sign_set`，
  保活统计 `ka_counts` / `ka_ok_count` / `ka_fail_count` / `ka_last_time` / `ka_last_result` /
  `ka_is_today` / `ka_note`，完成标记 `done_marked` / `done_mark`，
  任务快照 `task_snap_get` / `task_snap_set`（签到层据此判断「任务四元组变了没有」），
  通知标记 `notify_marked` / `notify_mark`（事件名 `fail` / `nosign` / `late` / `miss`；
  notify 层的 `failsign` 与 `failtask` 都映射到 `fail`），
  冷却基准 `nt_cooldown`，
  守护进程存活判据 `daemon_pid`（`status` 的「守护进程」行、`webstate` 的 `daemon=`、`start` 的单实例
  判定、`stop` 的杀进程目标四处共用它；判据是「/proc 里在 + cmdline 含 `fafu_checkin`」两条都成立，
  只看目录会把被回收的 PID 与僵尸进程读成「运行中」，而照 PID 文件直杀还可能误杀别人的进程）。
  文件名、字段名、字段顺序、内容格式是**对外契约**（升级后不丢当日记录），
  「按日滚动」的四处判定（保活统计、完成标记、通知一日一次、任务快照）也都只在本层发生。
  **唯一例外是 `service.sh`**：它是开机脚本、不加载库层，只在启动前读一次开关文件——
  读的是同一份 `disabled` 字面量，格式未变即不受影响；用一条断言
  （`tests/state.sh` 的「state · 收口边界」）钉住「只有 state 层与这一个例外持有状态文件名」。
  日志、PID 文件与 api 层的三个接口旁路文件（`.fafu_api.err` / `.fafu_api.hdr` /
  `.fafu_api.raw`，见 §2.3）不属于状态，分别由 base 层、入口与 api 层自己持有；
  PID 文件的**写入**归入口（`echo $$ > "$PIDF"`），**判读**归 state 层的 `daemon_pid`。
- **日志分级只作用于「写日志文件」这一处**：两档由配置层的 `DEBUG`（`0` / `1`，默认 `0`）决定，
  默认档留结果与原因、调试档写回完整现场。**写明归属靠文案，不认行号**——「留在默认档」就是
  **不给这一行加任何判定**（`log` 两档都写），降级只有两种手段：把那一行改走 `logd`，
  或让它在默认档被当日去重挡掉（`log_once`）；**文案一个字都不改**，两档逐字一致
  （判据与逐行归属见 §3.5，论证见 §2.1.2）。
  级别不作用于别处：只读状态输出的日志尾部、页面显示的最近几条日志、`status` 的最近日志，
  都不做级别过滤；api 层那三个旁路文件与保活统计文件里的 token 明文也不受影响（见 §2.3）。
  **生效值在入口装配时读一次**（`cfg_load` 落定，与其余 8 个键同语义；判定函数随后每行现取，
  所以「读一次」指的是配置的来源、不是只在启动时判一次），故改后需重启守护进程——页面保存路径本来就会
  停止再启动守护进程，所以在页面上改完即时生效。
- **网络调用只经 api 层**：`api()` 负责拼 URL 与签名，**真正发起请求的只有 `http_post()` 一处**
  （wget 的调用参数、`Authorization` 头、被丢弃的 stderr 都写在它里面）；`-T` 超时选项在
  api 层**加载时探测一次**（`WGET_T`）供它使用——探测与调用同层，改网络行为不必跨层找。
  其余层不拼签名、也不直接调网络：`tests/api.sh` 用一条**命令位**判据（行首缩进后的真实调用，
  注释里提到 wget 不算）钉住「命令位的 `$BB wget`/`curl` 全程序只有一处、且只在 api 层」。
  这条缝也是测试的注入点：断言里覆盖同名函数就能离线构造响应体 / 失败 / 超时（见 §5.1）。
- **设备命令只经 device 层**：屏幕状态判定、前端任务枚举、打开打卡页、移除打卡页任务只写在
  `lib/device.sh`，其余层不直接调 `dumpsys` / `am`（`tests/device.sh` 用命令位判据钉住；
  唤醒与熄屏用的 `input` / `wm` 仍在 `keepalive` 层，加固判据一并覆盖它们）。
  两条行为不变量在层内落地（论证见 §2.1.2 的 device 层）：**屏幕判定失败一律按「亮屏」处理**
  （无输出或字段名不认识时返回 0，避免误判成熄屏走静默刷新）、**绝不主动切换用户前台**
  （清理不彻底只记一行「保留在后台」，不再有任何「回桌面」动作）。系统命令的 fd 加固逐处一致
  （见 §3.1）：`dumpsys` 的输出**经变量承接或就地接管道都可以**（`screen_is_on` 是前者、
  `_activity_records` 是后者），不变量是**命令自身的 fd 不流进 `/data/adb`**。
- **缺层即响亮失败**：任一层缺失或不可读时，入口往模块日志写一行
  `模块不完整：缺少库层 <路径>` 并以非 0 退出。半装（入口在、层少一个）是最难排查的失败模式，
  宁可启动失败，也不要「某些功能悄悄不工作」。
- **打包与权限**：`build.sh` 把 `lib/` 一并打进 zip 并逐个核对产物；安装时脚本 0755、库层 0644
  （库层是 source 进来的数据，不需要可执行位）。
- **卸载不删库层**：`uninstall.sh` 只停进程、关页面、清理运行时文件，**不**删 `lib/`。模块目录随后
  由管理器整体移除即可；卸载脚本显式删自己的代码，一旦中途失败反而会留下半残模块
  （入口还在、层没了）——正是上面那条最难的故障。

### 2.1.1 通知机制

纯脚本模块没有自己的 App，通知只能借系统 shell 身份发出。机制与约束如下（均为源码/实测结论）：

| 事项 | 结论 |
|---|---|
| 发送命令 | `cmd notification post -t "<标题>" "<tag>" "<正文>" -S bigtext` |
| **执行身份** | **必须降权 shell**：`su - shell -c '...'`。root 身份发出的通知在部分 ROM 上被静默丢弃（实测 HyperOS 2 / 小米 13 Ultra：命令 `rc=0`，通知栏无任何显示），换 shell 身份后正常出现 |
| **降权探测必须验语义** | `su - shell -c CMD` 在 **KernelSU** 上会让 `-c` 落空：它用 Rust `getopts` 且默认 `StopAtFirstFree`，长度 1 的 `-` 是 free 参数、在那里就停止解析，最终 exec 出**交互式登录 shell**、把 CMD 当多余参数丢掉；`</dev/null` 下立刻 EOF 退出 **0**。只看退出码会记成「可用」，之后每条通知都变成「rc=0 但什么都没发生」。故 `probe_su` 先用 `command -v` 解析出 `su` 的实际路径，再用它依次尝试 `- shell -c` / `shell -c` / `shell /system/bin/sh -c`，并以 `id -u` 输出必须等于 **2000** 为准 |
| 通知 id | **恒为 2020**，不可指定 → 只能靠 `tag` 区分事件；**同 tag 会覆盖**（静默更新，不产生新提示音） |
| channel | 恒为 `shell_cmd`（名为 "Shell command"、重要性 DEFAULT），**不可调整**声音 / 震动 / 图标 |
| 通知归属显示 | 显示为 **Shell**（AOSP 自己的 manifest 里也专门申请 `SUBSTITUTE_NOTIFICATION_APP_NAME` 来给自己的通知改名） |
| ongoing / autoCancel / 按钮 | **均不支持**。通知会一直留在通知栏，直到被同 tag 覆盖或被手动划掉 |
| `POST_NOTIFICATIONS` 权限 | shell 命令路径自身不检查该权限，只校验调用方 uid ∈ {0(root), 2000(shell)} |
| 送达验证 | **`rc=0` 不能证明通知真的出现了**——这正是必须降权的原因。只能靠目视确认 |
| Doze 延迟 | 熄屏久了系统进入 Doze，通知投递会被批处理延迟，**22:00 / 22:30 的时间敏感提醒可能晚到**，不要当成精确闹钟 |

| 关闭页面的兜底 | **绝不主动切换用户前台**。这里原有一条「回桌面兜底」（`am start ... HOME`），它假定用户原本在桌面，于是移除不彻底时把正在用手机的用户直接甩到桌面（设备实测确认）。现改为：清理不彻底就让它留在后台 |
| 缩短中断 | 打卡页会**抢前台**（`open_page` 把它作为新任务启动，无法后台打开——`start-activity` 没有任何"不抢焦点"标志）。因此改为：**一拿到新 token 就立刻 `close_page`**，前台随即回到用户原来的 App，把中断时间从"等满轮询"压缩到"登录所需的那几秒"。拿不到 token 时不提前关页，保持原有兜底时序 |
| 「把原 App 提回前台」已实测否定 | `am start --activity-reorder-to-front` 被接受（回显 `flg=0x20000`）但**无效**：只给 `-n` 组件名、以及加 `MAIN`+`LAUNCHER` 两种写法都**新建任务**，从未复用已有任务。任务管理命令也不可用 → 不存在可行的"移动任务到前台"入口，相关代码已删除 |
| `am stack remove` 的行为 | 能把页面移出前台（前台自动回到用户原 App，这是当前方案的基础），但会**留下不可见的残留记录**（`visible=false`、`sz=1`），清不掉且无实际影响——这正是原代码当初写「回桌面兜底」的原因，**不要试图再"清干净"** |
| 任务管理命令 | 本机（Android 17 / SDK 37）`am task` 与 `am stack` 的子命令**均已不可用**（只剩 `Argument expected` 报错），因此不存在「把任务移到前台」的直接入口 |

**tag 策略**：含日期的「按日滚动」（如 `fafu-sign-20260914`），同事件次日覆盖前一天 → 通知栏条数恒有上限，不会累积。

**实现约定**：

- 业务层**只报事件名**（`sign` / `supp` / `seen` / `leave` / `failsign` / `failtask` /
  `nosign` / `late` / `miss`），tag 与文案都由 notify 层查表。新增一条通知要动三处
  （事件表 `_NT_TPL_*`、tag 表 `tag_of`、`_msg_*` 文案），但都在这一个文件里：
  - `tag_of()` 事件名 → tag 后缀（完整 tag = `fafu-<后缀>-<当日 tag>`），默认后缀就是
    事件名本身。两个例外是**对外契约**：`seen` 与 `sign` 同用 `sign`（同为「已签到」，
    同日互相覆盖不堆积）、三个未签时点用 `t2200` / `t2230` / `miss`；
  - `notify_event()` 取文案模板并发送。文案模板集中在 `_msg_*()` 系列函数里，
    正文**不含引号与命令替换**，可安全直接展开；
- 所有发送统一走 `notify()` / `notify_event()` / `notify_once()` / `notify_warn()`；
  `notify()` 负责构造命令串，**执行那一步单独放在 `nt_send()`**（与 api 层的 `http_post`
  同理）：改执行方式、或在断言里截住「最终交给系统执行的命令」都只动这一处；
- `probe_su()` 在**启动路径与表里标 1 的子命令**上探测一次降权写法（探不探由 `cmd_probe_needed`
  按命令表判，见 §2.2）：先用 `command -v` 解析出 `su` 的实际路径（`SU_BIN` 是回退与注入点，
  默认 `/system/bin/su`），再依次尝试
  `<su> - shell -c`、`<su> shell -c`、`<su> shell /system/bin/sh -c`，
  **以 `id -u` 输出等于 2000 为准**，结果写入 `$SU_MODE` 并记入启动日志 `notify=[...]`；
  由 `start` 派生的守护进程通过 `FAFU_SU_MODE` 继承该结果，不重复探测；
- 探测必须发生在任何子命令分支**之前**——各分支做完就 `exit`，探测晚一步就是永远执行不到的死代码。
  这条现在是**结构上的必然**（见 §2.2 的命令表）：入口按表先探该探的（装配阶段那一跳，
  `start` 与不带子命令必探），`cmd_dispatch` 再按同一列兜底探一次（只在没继承到时），
  两处都排在任何处理函数之前，没有「先分发还是先探测」的余地；
- 「首次失败」类通知有两个事件名（`failsign` / `failtask`）：文案与 tag 各不同，
  但**共用同一个当日标记**（`_NT_MARK_failsign` / `_NT_MARK_failtask` 都指向 state 层的 `fail`）；
- `notify_once()` **先发送、成功后才经 state 层落标记**：反过来的话一次瞬时失败会让该类提醒整天不再出现；
- 三个未签时点各自独立标记（`nosign` / `late` / `miss`）——共用标记会让 22:00 那条
  把 23:00 那条「今晚未能自动签到」永久挡住；
- 预警冷却（`notify_warn`）的判定与落盘都在 notify 层；基准经 state 层的 `nt_cooldown` 保存，
  **不能放普通变量**：`refresh_token` 总在 `$( )` 子 shell 中调用预警，变量赋值会随子 shell 丢弃；
- `notify_warn()` 的返回值就是「这次到底发没发」：**0 = 真发了**，非 0 = 被冷却挡住 /
  通知关闭 / 降权不可用。`refresh_token` 据此决定要不要 `sleep NOTIFY_LEAD`
  （没发还等，等于每次亮屏刷新都白等 5 秒）；
- `PL`（日期 tag）在主循环中每轮重算，避免守护进程常驻跨日后 tag 仍停在启动那天；
- 预警使用的提前量 `NOTIFY_LEAD` **只在屏幕已亮时生效**（`notify_lead()` 自带判断），
  熄屏路径不做无意义的等待。

> 已实测可用的降权写法（小米 13 Ultra / HyperOS 2 / SDK 37）：`su - shell -c '...'` 与 `su shell -c '...'` **均可**，
> 探测会优先选前者。注意 `su` 由各 root 管理器自行实现，不同设备行为可能不同，故不硬编码。

**为什么是 `cmd notification post`（而非 APK 或 `app_process`）**：

本模块是纯 Shell，**不携带任何 APK/dex**——这是安装轻、更新简单、卸载无残留的前提，也是本方案要守住的东西。
`cmd notification post` 的能力被 AOSP 硬编码限死（见上表：id 恒定、channel 恒定、无 ongoing），
而 `app_process` 跑 Java 能拿到完整的 `Notification.Builder`。**因此一个只看代码的读者会认为后者才是正确选择**——
下面记录被否决的方案与否决理由，避免重复提议：

| 被否决的方案 | 否决理由 |
|---|---|
| `app_process` + `ActivityThread.systemMain()`（参考 KernelSUGrantToast） | 能力完整（可自定义 id / channel / 图标 / ongoing），但要往模块里塞 APK、安装时抽出 `classes.dex` 与 `.so` 再删掉 APK，并引入 `HiddenApiBypass` 解除隐藏 API 限制。对「只发几条固定文案的提醒」而言代价过大，且破坏上面的无 APK 前提 |
| `am broadcast -a android.intent.action.SHOW_TOAST` | 查不到任何 AOSP 源码或官方文档支持该 action 存在（检索到的资料指向的都是 `cmd notification post`），**不可移植，不予采用** |
| `service call notification ...` | 依赖逐版本、逐 ROM 不同的 binder transaction code，且 Android 12+ 对 transaction code 增加了校验，脆弱性过高 |

> 若日后确实需要 ongoing / 按钮等能力，只能整体转向 `app_process`：那是模块结构与构建方式的改动，不是改几行，
> 因此这个选择的切换成本很高——改之前请先读完本节与上面的限制表。

### 2.1.2 层内实现注记

代码里只剩结论，**论证在这里**。按加载顺序归档，每个小节一层；跨层的坑（系统命令重定向、
网络工具差异、时区与时间源）不在这里重复，见 §3.1 / §3.2 / §3.3。
本节的每一条都与代码核对过：实测类结论带来源与日期，核对不实的没有写进来。

**入口（`fafu_checkin.sh`）**

- **降权探测必须排在装配阶段。** 守护进程是入口 `cmd_start` 用 `nohup` 派生出来的后台进程，
  它自己不再探降权写法，只能经环境变量 `FAFU_SU_MODE` 继承；漏探 = daemon 的 `SU_MODE` 为空
  = `notify()` 直接返回 = 自动签到那几条通知**全部静默消失且没有任何报错**。
- **轮询范围只决定「什么时候去查看今晚的任务」。** 该不该签、能不能补签仍只由服务端任务数据决定，
  范围不是签到判据。两个端点由入口在循环外取一次快照（`POLL_START` / `POLL_END`），
  入口读的是读取函数的返回值，不是配置层那个同名变量。
- **`signin_remind_notask` 必须排在「任务异常就跳 4 分钟」之前。** `rc=2` 恰恰就是「取不到任务」
  ——也就是最该喊这条兜底的情形；把跳档写在前面就会把它静默吞掉。
- **时刻比较直接用 `now_hm` 的零填充字符串**，字典序即时间序，不必换算成分钟；
  两条否定合起来读作 `POLL_START <= now <= POLL_END`（`test` 没有 `>=` / `<=` 的写法）。
- **退避只有 60 与 240 两档**（`rc_wait=60`、任务异常档改 240），**没有「把本轮休眠改短」的分支**。
- 入口内联的时点与间隔只剩三处：描述自检 `DESC_TICK=10`、日志轮转 `ROT_TICK=60`、
  休眠基数 `60` 与异常档 `240`；其余窗口与节流都由 keepalive 层判定。

**base 层（`lib/base.sh`）**

- **日志分级只有一条判据：频率 × 信息量。** 分钟级重复且内容不变的行降级到调试档；
  每日一两次的、即使偏诊断也留在默认档。这条判据就是**以后新增日志时的默认归属规则**——
  新写一行日志时先问「它多久出现一次、每次带来什么新信息」，不必每次重新开会决定它属于哪一档。
- **四个写日志出口，共用 `_log_write` 一个落地处**（`>> "$LOG"` 只有这一处）：
  `log`（**两档都写**）、`logd`（只在调试档写）、
  `log_once`（失败行：默认档当日只留首次、原因变了再留一条，重复轮次降级到调试档）。
  **档位判据只在 `logd` 与 `log_once` 上**：判定的是「哪些行降到调试档」，
  所以「留在默认档」= 那一行**不加任何判定**（照旧走 `log`），而不是「换一个默认档专用出口」。
  **不引入第二条写日志路径**：判定都只在出口这一层，业务层只挑一个出口；
  三个出口落地的是同一行，所以「文案即契约」这条不会被档位破坏。
- **档位必须懒解析，不能在加载时读进常量。** 配置层的 `cfg_load` 在入口里排在**层加载之后**，
  若在加载时把档位读成常量，它会永久停在默认值 0——表现是「配置页明明开了调试档，
  日志却一行都不多」。故判定收成一个**每次现读的小函数**（`_log_debug_on`），不缓存。
- **base 层读档位只能直接读生效值变量，不能调配置层的读数函数。** base 是第 1 层、
  config 在第 2 层，`cfg_effective` / `cfg_debug` 都是**更后层**的函数——调它就是反向引用，
  层序守卫会报违规（§5.1 的 `tools/check-layer-order.sh` 那一条）。可行的写法是**直接读
  与键同名的生效值变量**（配置层把生效值就放在那个变量上）：不碰任何更后层，也仍是懒解析。
  代价是「生效值变量名」成了两层的隐含契约——改配置层的赋值方式时要想起这里。
- **三个出口都必须「恒返回 0」**。不写行的那一档若返回非 0，
  `log … ; return $?` 这类调用点会把「这行没写」误读成「这一步失败」——日志档位于是变成一条
  **功能性**分支，而「级别只作用于写日志这一处」正是要避免这件事。故判据写完各自显式收尾
  （`logd` / `log_once` 以 `return 0` 收，`log` 写行那一支也以 `return 0` 收），
  **别把出口的返回码留给 `>> "$LOG"` 的去向决定**。
- **降级行只能改成 `logd`，绝不改文案**（文案即契约，见 §3.5）。`log_once` 在默认档写下的
  那一行与升级前**逐字相同**——于是「按文档去查某一行」在两档下都成立。
- **`log` 的语义是「两档都写」，不是「只在默认档写」**：它不做任何档位判定，
  函数体就是 `_log_write` 那一跳（收尾补 `return 0`，见上）。写成「默认档专用出口」会让后来的人
  以为默认档另有一条路径，进而为它加出第二套判定——这正是「级别只作用于写日志这一处」要挡住的。
- **token 打码落在本层**（第 1 层，与 `tz_offset` / `ms_to_hm` 同性质：纯函数、不依赖任何更后层）：
  **公开名只有一个 `tok_mask`**——打印点统一写 `$(tok_mask "$token")`。
  **不再有 `tok` 这个短别名**：它只是纯转交，而 `$tok` 这个变量名在打印点周围到处都是
  （`tok=$(get_token)`），两个名字并存时读代码的人要先分辨「这是函数还是变量」；
  一个名字 + 一条形状真源更省事，也让「哪些地方打了码」可以一条 `grep tok_mask` 数清。
- **打码的形状与边界**（`DEBUG=1` 原样明文；`DEBUG=0` 走下面这套）：
  ① **按长度判、不假设 token 一定以 `2_` 开头**——先扣掉 `2_` 前缀（**有才留它**），
  再从**扣掉前缀之后的正文**里取尾 4 位；扣掉前缀后**恰好 4 位**的那一档留下的就是它自己
  （形状不为此单开一档），**不足 4 位**则整串打码成 `****`——**连 `2_` 前缀一起隐身**。
  前缀本身不是秘密，但「整串打码」的意图就是不泄露任何片段，故短 token 不会留下 `2_`。
  ② **空输入输出空**：调用方既有的 `[ -n "$tok" ]` 判定不受影响（返回空而不是 `****`，
  否则「没有 token」会被显示成一个像是打码过的 token）。
  ③ **只作用于显示，绝不覆盖 token 变量本身**——覆盖了接口调用会带着打码串发出去，签到直接坏掉。
  保留尾 4 位是为了「看得出换没换」：打码前后不一致就是刷新成功过。
- **打印点是 13 行 / 15 个调用**（逐处写 `$(tok_mask "$token")`，别改成覆盖变量）：
  keepalive 层 **8 行 10 个调用**（刷新成功两侧、未取得新 token、保活心跳、保活失败三档、
  静默刷新成功两侧、静默刷新未成功）、命令层 **5 行 5 个调用**——`cmd_refresh` 的 `✅ 刷新成功` 1 行、
  `cmd_keepalive` 2 行（`token 有效` / `调用未成功`）、`cmd_status` 的 `token:` 2 行。
  **`cmd_refresh` 那一处最容易漏**（它属于命令层、不在原清单里），
  漏了就等于手动刷新时仍然吐明文；`grep -c 'tok_mask' lib/*.sh` 就能核对总数
  （`base.sh` 那 1 处是**定义行**，其余 15 处才是打印点）。
  授权头本来就不落日志（响应头白名单不含它），所以默认档没有别的暗路。
- **两处「不能动」的边界**：保活统计文件里那份 token 明文**保持不动**（见 §2.3）——
  它是运行时状态、被当值取用，打码会直接写坏统计；`webstate` 那一行**压根不打码也不用打**，
  它只报有效性、明文从不进输出。
- **取「现在几点」只有 `_now` 这一个入口**，把 `$BB` 指向替身即可整体拨钟。**但别写成「各层一律
  不再自己调 `date`」**：`lib/commands.sh` 与 `lib/api.sh` 里各有一处直接调用（本轮只记录、未修）。
- **设备那份 busybox 的 `grep -oE` 在若干模式上直接段错误（exit 139）。** 后果极隐蔽：字符串字段在
  真机上恒为空串——不报错、不断链，数字字段全对，只表现为「日志里少个任务名」。故取字段一律用
  参数展开（`case` 判存在 + `${1#…}` / `${1%%…}` 裁剪），顺带省掉每字段一次 fork。
  依据：提交 `0826f5f` / `0c22eb4`（2026-10-12）与 `62a4579`（2026-10-13）。
  CI 用的是与设备同一份 KernelSU busybox，故 CI 能复现；本机那份是另一构建、跑不了设备版 ELF，
  复现不出**不作为反证**。
- **参数展开里的模式写法也只有一种形状能用**：取「带引号键」的值要写成
  `${1##*"\"$2\":"}` 这种「引号在里面、外面再包一层引号」的形式；写成裸的 `${1##*\"$2\":}`
  时这份 ash 直接报 `unterminated quoted string`（本机 Windows busybox 1.38 同样报，
  Ubuntu 的 dash 不报——两个环境都会踩，别只在一个里试）。`case` 的模式里同理。
- **`json_first` / `_json_val` 的裁剪是唯一的取字段实现**；不要改回 `grep` / `awk` / `sed`（见上一条）。
- **经纬度取「最后一次出现的形状合法值」，不切块。** 顶层与 `signInStudent` 内各有一份 `lng`/`lat`，
  真值在后一份；顶层那份是**字符串** `null`，先撞上它就会把 `lng=null&lat=null` 发出去、被服务端回 400
  （正文 `Content-Length: 0`）。切块取要先假定对象不嵌套（块里出现 `{` 就截错），而
  「两份坐标的先后」是接口的实现细节、会变；按形状取值，接口怎么变都还取得到真值。
  依据：提交 `ddb88c8`（2026-10-13，正文写明「顶层 null 曾被当成值发出去」）。
- **`tz_offset` 绝不输出空；取不到时给哨兵 `--`。** 空值会让日志里的 `TZ=[…]` 退化成 `[未设/]`，
  读的人分不清「没取到偏移」与「偏移为零」。`date +%z` 拿不到时的退化路径只输出旁证写法
  `--(+6)`（给日志肉眼判断，只到小时），**不当作偏移交给 `tz_offset_s`**：这条路的前提就是本机时区
  不可信，而「差值恰好为 0」与「真在 UTC」无法区分。`tz_offset_s` 判不出来一律给空，
  调用方（`ms_to_hm`）随之不写钟点，而不是按 UTC 写一个偏几小时的钟点。
  依据：提交 `62a4579`（2026-10-13）——CI runner 在 UTC、开发机在 +0800，同一条断言两边结果不同
  （假红 / 假绿），故断言改用替身把 `MOCK_TZ` 输入钉死，覆盖 `+0545` / `+0000`（UTC 上的合法零偏移）/
  `-0530`。
- **偏移形状的 `case` 一律写成逐字符写法**（`[+][0-9][0-9][0-9][0-9]|[-][0-9]…`），
  **不要用 `[+-]`**：这份 ash 把它当区间，不是两个字符。依据：提交 `62a4579`（2026-10-13）。
- **凡把 `HH` / `MM` 送进 `$(())`，先用 `${h#0}` 剥前导 0**，并补 `[ -n "$h" ] || h=0`
  （`"00"` 剥完是空串）。POSIX 把 `08` 当八进制，本机 busybox 1.38.0-FRP 上 `$((08))`
  直接报 `sh: arithmetic syntax error`。
- **钟点换算用纯算术，不用 `date -d @<epoch>`。** 设备上 `date -d` 给的是错值，而**同一次**探针里
  `date +%s` / `date +%z` / `now_full` 全是对的——错的是「某个戳是几点」这一步。
  依据：**2026-10-13 真机探针**——`date -d @1791811959 +%H:%M` 给 `17:09`（正确 `21:32`）、
  `-u` 给 `09:09`（正确 `13:32`）、`-d @0` 给 `08:00`（正确 `00:00`）；提交 `41556db`（2026-10-13）。
- **`ms_to_hm` 的参数用 `${2-0}` 而不是 `${2:-0}`**：要分开「**没给**」（省略 → 当 UTC 用 0）与
  「**给了但为空**」（判不出偏移 → 输出空、不写钟点）；写成 `${2:-0}` 会把后者当成 UTC，
  写出一个偏几小时的钟点。依据：本机 busybox 1.38.0-FRP 实测 `f a` → `[0]`、`f a ""` → `[]`。

**config 层（`lib/config.sh`）**

- **生效值存在与键同名的变量里，本层对它的赋值只经 `_cfg_set` 一个出口**（先落登记表默认值、
  `cfg_load` 按配置文件覆盖、起止颠倒时整对退回默认）。不数调用点——数了就会随调用点增减而漂移。
- **取值默认走 `cfg_*` 读取函数，但直接读同名变量的有四处**，且各自有理由：命令层的两处读 `$NOTIFY`
  （通知开关的生效值就落在同名变量上，读变量与读 `cfg_notify` 等价）、入口那一处读 `$POLL_START` /
  `$POLL_END`（轮询范围在循环外只取一次快照）、**base 层 `_log_debug_on` 读 `$DEBUG`**（日志档位）。
  最后那一处有两条硬理由：① base 是**第 1 层**，调配置层的 `cfg_effective` / `cfg_debug` 就是
  反向引用，层序守卫会拦；② 它**不兜第二份默认值**——写成 `[ "$DEBUG" = "1" ]` 而不是
  `[ "${DEBUG:-0}" = "1" ]`，`DEBUG 0` 的默认值只在配置层登记表里有一份，`_cfg_defaults`
  在配置层加载时就已落好。这正是上面那条「不再各自写 `${VAR:-默认}` 兜默认值」的**字面落地**：
  读的就是登记表落好的那个值，缺了它只能是「配置层没加载」，而不是「这里另有一份默认」。
  `tests/config.sh` 的「默认值只留一处」那组因此多了两条反向守卫（钉 base 确实读 `$DEBUG`、
  钉全程序没有 `DEBUG:-` 形状的第二份默认值）。**不要写成「其余层一律不直接读」**。
- **「读回兜底」与「写入拒绝」不能合成一条路。** 写入要的是「要么全改、要么不动」的确定性
  （校验全部先于落盘，任一项不合格就整批拒绝，每一次 `return 1` 都排在 `write_atomic` 之前）；
  读回要的是「怎么坏都不崩」的可用性（坏文件——只有手改能造出——不拒绝、不报错，逐键退回默认值，
  因为程序仍要照常跑起来）。合并会把「拒绝写入」变成「静默改写用户的文件」，
  或让一个手改坏的文件直接让程序起不来。
- **`DEBUG` 是登记表里的一行，不是一处特判。** 键名与默认值只写在登记表里；`cfg_valid` 把它与
  `KEEPALIVE|NOTIFY` 并成一档（开关项，只认 `0` / `1`），`cfg_reason` 的对应分支同样并入——
  于是「默认值代入、非法值退回默认、写入闸门整份重写、回读回显」四条既有机制自动跟着表走，
  一行都不用另写。**新增档位时照抄这条：加键 = 加一行 + 并进开关那一档**，
  不要为它单开第二种校验形状（形状一多，页面、闸门与运行时看到的三份语义就会漂移）。
- **档位只能现读，不能缓存。** 本层按契约提供读数函数 `cfg_debug`（内部就是
  `cfg_effective DEBUG`），供**更后的层**使用；不落任何缓存变量。理由见 base 层那条
  （日志出口比 `cfg_load` 更早存在，缓存会永久停在默认值 0）。
- **base 层不调 `cfg_debug`，它直接读生效值变量。** 这是同一份值的第二条读法，也是
  **唯一的例外**，理由是层序：base 是第 1 层，调第 2 层的函数就是反向引用。
  生效值变量与键同名这一点因此成了跨层的隐含契约——改本层的赋值方式时要想起 base 层的日志出口。

**state 层（`lib/state.sh`）**

- **开关文件用原子写**：它是「停用 = 不再有任何网络请求」的唯一依据（`service.sh` 启动前读一次、
  守护循环每轮读一次），所以宁可保持旧值，也不要让半截内容被读成「启用」。
- **通知标记的粒度：四类通知各自独立，而「已取得任务」与 nopub 提醒刻意共用一份。**
  `fail` / `nosign` / `late` / `miss` 各有自己的当日标记文件；共用会让先到的那个时点把后面的永久挡住
  （「主窗口还剩 30 分钟」先发了，「补签截止」就再也发不出去）。反过来 `.fafu_task_seen` 是
  「真的取到任务」与「已经为此提醒过」共用的同一个文件——两者是同一份事实的两个入口，不是两套机制。
- **任务快照的日期键由本层按今天填，调用方不必知道它存在。** 快照整份写入、按键读；读判定先看日期键
  是不是今天，不是今天即视为「没有快照」，于是跨日后不会拿昨天的任务当今天的比较基准。
  它与保活统计、完成标记、通知标记三处的按日滚动同源，这也是四处判定都留在本层的原因。

**api 层（`lib/api.sh`）**

- **成功判据是「curl 优先、wget 兜底」**：有可用 curl 时按 HTTP 2xx 判成功（4xx/5xx 也算失败，
  否则服务端的报错正文会被当成正常响应体交出去）；走 busybox wget 兜底时沿用 wget 的退出码。
  调用方（`api` 的使用者）只看 `http_post` 的返回码，不 grep 响应体。
- **为什么只能由 `http_post` 自己收失败原因**：工具的 stderr 由它落到旁路文件，`api` 在**确认失败**后
  才读首行转交出去。不能让调用方重定向 stderr 去收——`api` 函数体内的任何 stderr 都会进去
  （`set -x` 追踪、子命令提示行），首行可能是 `+ local url` 而不是那句报错。
- **为什么必须同时留下状态码与正文**：只留状态码的话，正文为空时「服务端拒绝 / 连接失败 / 超时」
  三种事后仍然分不出来。
- **探测「认能跑、不认文件在」**：`[ -x ]` 只证明文件存在，不证明能跑；必须真的跑一次 `--version`
  并看退出码，否则「存在但起不来」的 curl 会被当成可用，于是每次请求都失败、又看不出原因。
  候选自上而下：PATH 上的 `command -v curl`（终端里常由管理器挂进来）→ `/data/adb/curl`
  （想固定用某一份时放这里）→ `$MODDIR/curl` → `/system/bin/curl` → `/system/xbin/curl`。
- **探测与调用都要清掉 `LD_LIBRARY_PATH`**：管理器的终端会往它里面塞自己的旧 libcrypto，
  动态链接器优先加载后同一个 `/system/bin/curl` 会因找不到符号而起不来。它只影响查找路径，
  清掉不改变请求语义。
- **响应头白名单为什么只有四项、且顺序固定**：整包头会把日志行淹掉；服务端没给的那项**不出现**
  （不写空占位），四项一个都没有时整段不输出；顺序按白名单固定，于是同一份响应头每次落出的字面量
  都一样，肉眼比对与机器比对都不必猜顺序。
- **不许自己拼 `hdr=`，取值也不许用 `sed`**：上层要把那一行里的响应头（`Date`）并排到自己的日志行上时
  走只读访问器，它给出的就是 api 层落下的同一份字面量——自己拼就会多出第二个格式真源。
  BRE 里裸的 `{` 是区间运算符的起始符，各家实现对它并不一致，在设备那份 busybox 上取不出来；
  参数展开是纯字节裁剪，不经过任何 applet。
- **计时读数是三级来源，位数就是单位**：① `date +%s%3N`——`%N` 是 busybox 的**可选特性**，
  没编进去时 `date` 把 `%3N` 原样吐出来、数字串里因此多一个 `3`，故只认「≥13 位」并截前 13 位；
  ② `$API_UPTIME`（默认 `/proc/uptime`）——两位小数＝10 毫秒精度，它是开机以来的秒数而非墙上时间，
  但两个读数只用来相减、与 ① 等价，为共用「13 位＝毫秒」而左补零到 13 位；
  ③ 两者都拿不到 → `date +%s`，10 位读数、单位按秒。`_api_cost` 只按位数判、不认来源。
- **诊断行末尾两段读数的判据只有一个：`_api_part <诊断行> stable|hdr`**，
  两个薄壳各取一半——`_api_cause` 取 `stable`（给上层的失败原因键用）、
  `_api_hdrs` 取 `hdr`（给展示行并排响应头用）。这是与 `json_first` / `_json_last` 同一形状的
  「一处形状、两个消费者」：**并上日志行的那段响应头与失败原因键认的是同一段真读数**，
  不存在两套截法各自漂移的余地。
- **为什么锚在末尾、且要尾巴收在 `}`**：段序由 `_api_note` 定死
  （正文 → `err=` → `hdr={…}` → `耗时=…`），故两段都**从最后一次出现处认**
  （`##` 取最长前缀、`%` 取最短后缀，同一处对齐），并且**尾巴确实收在 `}` 才算一段 `hdr=`**。
  于是正文里恰好含 ` hdr={` / ` 耗时=` 这类同名字样时，认出的仍是那两段真读数——
  夹具 `sg_poison` 就是往正文里塞回显的日志形状字样，专门守这条。
- **`_api_cause` 剔掉的是两段「这一次调用的读数」**：`hdr={…}` 与 `耗时=…`。
  **剔的不止耗时——`hdr={…}` 里的 `Date` 是服务端回这一条时的钟点，每轮必然不同**；
  只剔耗时的话，4xx/5xx 那一档（服务端必然给 `Date`）的当日去重会**直接失效**：
  同一晚同一条失败每轮都被当成新原因。留下的部分是状态码 / 网络退出码 / 正文 / 报错原文——
  它们才是「为什么失败」。做法仍是纯参数展开，**不拿 applet 解析结构化文本**，也不自己拼诊断行。
- **`_api_cause` 只算「原因」，不改「写什么」**：日志行本身仍带着完整的那一行事实
  （`hdr=` 与 `耗时=` 一个都不少）——去重只管写不写，不管写什么（见 base 层的 `log_once`）。

**device 层（`lib/device.sh`）**

- **`dumpsys` 的子命令必须原样透传。** 写 `dumpsys activity` 打印的是**服务概览**，里面没有
  `ActivityRecord` 可解析；必须是 `activity activities` 两个参数原样透传。改写成「只取 `$1`」或
  「拼成一个词」都会让任务枚举恒为空——而恒为空的失败形态是「清理不掉页面」，不会报错。
- **`screen_is_on` 检测失败为什么按「亮屏」处理**（命令缺失 / 无输出 / ROM 改了字段名时返回 0）：
  同一个 `WAS_ON` 决定三件事，**误判成熄屏**的代价是立刻可见的——先弹页面、后补预警那条路径被跳过
  （用户的屏幕明明亮着，页面却毫无解释地跳出来），收尾还会把屏幕恢复成「刷新前的样子」，
  于是 `input keyevent 223` 把用户亮着的屏幕关掉。反方向（真熄屏被判成亮屏）只是少一次唤醒兜底、
  白等一轮——静默开页在熄屏下本来就能拿到 token。两条路一比，「检测失败按熄屏」的坏后果更重。
- **`open_page` 为什么必然抢前台**：打开打卡页只有 `am start`（start-activity）一条路，它没有任何
  「不抢焦点」标志，页面必然进前台。模块的对策不是避免抢，而是**把抢占窗口压短**：调用方一拿到
  新 token 就立刻 `close_page`。
- **为什么收尾绝不切前台**：`am stack remove` 之后可能留下不可见的残留记录（`visible=false`），
  清不掉时**只记一行日志**，绝不做任何「回桌面 / 切前台」的动作——主动切前台会把用户从正在用的
  App 里踢出去，比留一条看不见的残留糟得多。
- **任务号在活动记录里出现两处**（`u0 ` 之后与记录末尾 `}` 之前），两处取到的是同一个号。
- **本层两处 `grep -oE` 是「不拿 applet 解析结构化文本」那条经验的例外**（见 §3.3）：它们的用途是
  把 `dumpsys` 输出裁成「一条记录一行」与「任务号」，模式里不带空格、不做语义解析。
- **本层的日志归属成对出现**：`页面关闭检查: 残留活动=N` 降级到调试档，而
  `页面移除未彻底(残留N)，保留在后台（不再回桌面）` 留在默认档。理由是同一条判据的另一面——
  正常时残留恒为 0，「检查」那一行零信息量；而**真残留**时才写的「移除未彻底」解释的是
  使用者看得见的行为（页面没关掉），必须留下。**只降检查行，不要连未彻底那一行一起降**。

**notify 层（`lib/notify.sh`）**

- **降权探测必须验语义**：判据是「命令真的执行了、身份真的降到了 shell」，即 `id -u` 读作 2000。
  只看退出码会把「rc=0 但命令根本没跑」的链路记成可用，之后每条通知都静默消失且没有报错。
- **`probe_su` 为什么用绝对路径而不是命令名**：`su` 的实际位置先由 PATH 解析、取绝对路径，
  探测与发送用同一个二进制；注入点只有 `SU_BIN` 一处——`su` 是 busybox 的内建 applet，
  PATH 上放同名文件拦不到它。
- **通知能力被系统限死在哪**：`cmd notification post` 的通知 id 恒为 2020（不可指定，只能靠 tag 区分
  事件）、channel 恒为 `shell_cmd`，重要性 / 声音 / 图标 / ongoing / autoCancel / 按钮均不可调；
  要这些能力只能整体转向 `app_process`（见 §2.1.1）。
- **tag 表的三条例外是对外契约**：tag 后缀默认等于事件名；例外三条必须保持——`seen`→`sign`
  （与签到同 tag，同日互相覆盖）、`nosign`→`t2200`、`late`→`t2230`。tag 含日期，整条策略是「按日滚动」。
- **模板表为什么必须显式写出来**：模板名同时是两处对外契约的一部分（tag 后缀、state 层标记名），
  故 `_NT_TPL_*` 是显式映射；让它跟着事件名走，等于把两处契约交给「函数名恰好相同」这种巧合。
- **两个「当日首次失败」事件名共用一个当日标记**：`failsign` / `failtask` 的文案与 tag 各不相同，
  但共用 state 层当日的 `fail` 标记——同类提醒一天只发一条。
- **兜底提醒复用「已取得任务」标记**：取到任务时它是「今天不用再问」，兜底发出去时它是
  「今天已经提醒过」——同一份事实，不另立标记。
- **`_NT_LEAD_MIN` 的兜底数与 signin 层的提前量常量是两处**：标题里的分钟数由 signin 层算好后传入，
  取不到时回退到标题里写死的那个数；它与 `signin_remind_lead_min` 的常量是两处，改一处要想起另一处。
- **通知冷却基准为什么必须落盘**：预警是在 `$( )` 子 shell 里发出的（`refresh_token` 的全部调用点
  都在 `$( )` 里），冷却基准若放普通变量，出了子 shell 就没了——冷却永远不生效，
  每次亮屏刷新都要白等提前量。故基准归 state 层落盘。
- **本层只降「可用」那一行**：`通知链路: 降权写法 […] 可用（id -u = 2000）` 是每次启动探测一次、
  结论不变的成功路径；而 `找不到 su` 与 `降权不可用` 是**失败路径**，它们恰恰解释「通知为什么
  没收到」，必须留在默认档。同理「通知发送失败」留在默认档——别按「通知层的行一起降」去改。

**desc 层（`lib/desc.sh`）**

- **改写 `module.prop` 前必须校验临时文件非空。** 回退路径用 `grep -v '^description=' module.prop >
  module.prop.tmp` 造新内容；这一次读取失败（权限、元数据被别的工具占住）会留下**空文件**，
  紧接着的 `mv -f` 就把 `module.prop` 清空——模块元数据全丢，管理器里连模块名和版本都不显示了，
  只能重装。所以 `mv` 之前必须先确认 tmp 非空，空则删掉 tmp 并以非 0 返回（调用方据此不改描述）。

**keepalive 层（`lib/keepalive.sh`）**

- **保活开关不在本层读**：本层只从配置层取保活时段（`cfg_ka_start` / `cfg_ka_end`）；
  保活开关 `cfg_keepalive` 的读取点在入口主循环与命令层。
- **1800 秒刷新冷却跨轮真的生效**：`keepalive_ping` 由入口主循环**直接调用**（不在 `$( )` 里），
  基准写在常驻守护进程的变量上。不要按「只在本轮有效」去把它改成落盘实现——那会把能用的冷却改坏。
- **刷新三段的两条时序不变量**：拿到新 token 就立刻关页（把前台尽早交还用户）；拿不到则**不**提前关页，
  留到唤醒重试之后由收尾统一关——提前关页会让第二段没有页面可等，也与兜底唤醒的时序不一致。
- **两种失败行为什么分得开**：失败行的说明段由本层给出 rc 与屏幕状态，随后**原样**接上 api 层留下的
  那一行诊断；「网络不通」（`net rc=` 加工具原话）与「登录态失效」（调用成功但响应里没有任务列表，
  带服务端状态码与正文）因此第一次分得开。
- **本层的日志归属**：心跳行（`保活: ✅ … token 有效`）降级到调试档，保活失败三档、刷新触发原因、
  唤醒重试、屏幕收尾两行、提前移除打卡页、刷新成功与「未取得新 token」、静默刷新结果两行**留在默认档**。
  判据仍是频率 × 信息量（见 §3.5）。

**signin 层（`lib/signin.sh`）**

- **「时间核对」那一行为什么要把这次换算用到的输入全记下来**：它一次记全**四类输入 + 两个现场**——
  `signTime`（服务端原值）→ `sign_time`（本地换算结果）、`now`（本机此刻）、`TZ`（含偏移）、
  `LDP`（库路径变量）、`alt`（按 UTC 视角的第二种解释），末尾再跟整条服务端记录与这一次查询的响应头。
  理由：时钟不对、时区库不对、库路径变量被管理器污染、取到的戳不对，四者都会给出同一个
  「`signTime` 与换算结果对不上」的表象；而「时区偏移是不是整点」是区分「时区库不对」与「时钟偏了」的
  第一判据（标准时区偏移必是整小时或半点），所以偏移量必须并排进 `TZ` 段。
  两个形状约束照抄：偏移量写在方括号**内**（既有形状断言按 `TZ=\[.*\] ` 读这一行）；
  `tz_offset` 保证不输出空。服务端记录超限时不静默截断，由 api 层补字节数与截断标记。
- **坐标的取值优先级**（提交时按序取）：`signInStudent` 内的坐标（最近一次签到的真实位置，
  服务端记的就是这一对）→ 任务顶层的 `lng`/`lat`（仅当它不是 `null` 时才可用）→ 内置坐标兜底。
  取法只能用 `_json_coord`（取最后一次出现的形状合法数值）。
- **提醒文案里的钟点只能走纯算术换算**，不能用 `date -d @<戳>`（见 base 层那条）。
  谁把它「顺手改回更自然的写法」，提醒文案里的钟点就会跟着错；缺值输出空，
  调用方据此不写钟点（而不是写一个假的 `00:00`）。
- **提交失败后的短重试为什么存在**：主窗口刚开的那几分钟服务端还没开始收——模块提交被拒，
  而同一分钟内手动提交能成功。主循环一分钟一轮，等于把这段窗口白丢，故**提交失败**后短等重来
  （`SG_RETRY_TIMES` 次、每次 `SG_RETRY_WAIT` 秒）。「不在时段」那一档走不到这里，
  所以窗口没开时不会把轮询催成高频。
- **「任务未发布」兜底提醒为什么必需**：三条截止提醒的锚点**全部**来自服务端任务数据
  （主窗口截止 / 补签截止），任务根本没发布时它们永远不会响，而那恰恰是最需要提醒的情形；
  故另有一条挂本地时钟、与轮询窗口无关的兜底，目标时刻 = `min(轮询范围止, 23:00)`，
  当日已取得任务就不再打扰。
- **`signin_parse` 为什么用 `eval` 把结果写回调用方的 `local`**：解析的输出走调用方声明的变量名，
  于是「从响应里取字段」只有一处实现，调用方拿到的是值而不是再解析一遍；层内局部名一律 `_sg_` 前缀
  ——与输出变量同名会被 `local` 影子化，`eval` 写回的就是自己（表现为判定拿到空状态、一路走错分支）。
- **`signin_fetch` 交出结果的形状与 `signin_parse` 同一手法**（`$2` / `$3` 是两个输出变量名，
  调用方先 `local` 好再传进来），**不再经 stdout 交两行**。这不是风格选择，是硬约束：
  调用方一旦写成 `out=$(signin_fetch …)`，这一步就整个落进**子 shell**，而失败行的当日去重状态
  （base 的 `_LOG_SEEN`）是**主 shell 的变量**——子 shell 里记下的「今晚这条已经写过」
  出不了子 shell，同一晚的失败会每轮重写一条，**去重等于没做**。所以 `run_once` 里是
  `signin_fetch "$(get_token)" tok resp` 这样**在主 shell 里调**、结果经 `tok` / `resp` 写回。
  改这里的调用形状前先想清楚「状态住在哪个 shell 里」。
- **本层的日志归属与两个反直觉的取舍**（判据见 §3.5）：
  ① **提交尝试行降级到调试档，而提交的失败与结果留在默认档**。尝试行信息量最高（完整响应体、
  状态码、耗时、响应头），但它每次提交都写、短重试还会连写几行，是「一天只有一次现场」这句话里
  唯一能刷屏的那一类；而它承载的信息**已经原样并进了失败行与成功行**（`_api_err1` 转交的那一段），
  所以降级它不会让默认档失去定位能力。**别顺手把失败行也降下去**——那才是真正只有一次现场、
  错过要等一天的东西。
  ② **「不在签到时段」降级，而「时间核对」留在默认档**：前者在窗口内每分钟一条且结论不变，
  后者每日一次、是唯一能解释「今晚为什么判定成还没到点」的行。
- **「应用数据暂不可读」与「应用数据已就绪」必须成对降级**。它们是同一次重启等待的头尾两行：
  只降其一，默认档里会剩下一行孤零零的「已就绪」（或「暂不可读」）而无从配对；
  等不到时会另写一行「未检测到应用数据（…）——稍后自动重试」，那一行**留在默认档**——
  它才是「读不到数据」这个结论本身。

**commands 层（`lib/commands.sh`）**

- **哨兵分发协议：输出与返回码必须分开走。** 处理函数以 `exit` 收尾，因此它的输出**不能**直接经
  `$( )` 承接——那样输出被吞掉、`$?` 里还会夹着文字。分开的办法是**一层命令替换 + 一行哨兵**：
  `{ "$handler" "$@"; echo "$CD_SENTINEL$?"; }` 跑在管道右侧的 `while` 里，返回码由哨兵行带回，
  再从末尾剥掉哨兵、把哨兵之前的内容原样送回 stdout。哨兵的值必须是不可能出现在命令输出里的串；
  它同时是「处理函数真的跑过了」的证据。
- **为什么不用 fd 3 承接输出**：**fd 3 是调用者的环境事实**——root shell（管理器的 WebUI /
  交互终端）常常就是关着 fd 3 exec 出本脚本的，而重定向一个未打开的 fd 会让整条子命令当场失败。
  分发路径必须不依赖任何外部 fd。
- **「探测与分发分成两段」是结构上的必然**：降权探测必须发生在**任何子命令分支之前**，
  且必须发生在**当前进程**里——处理函数跑在管道右侧的子 shell 里，在那里赋值 `SU_MODE` 留不下来
  （表现为「探测成功、通知却发不出去」）。
- **表里标 0 的七条不探降权**，理由不是「它们只读」：探测会往日志里写一行，而 `webstate` / `status`
  的输出里带着日志尾部（页面的「最近日志」），读状态那次调用会让页面第一条日志变成与自己无关的降权行。
  （标 0 的七条里 `toggle` / `enable` / `disable` 会改状态、启停进程，`stop` 会杀进程——
  别给这一档起「只读与配置写入类」这类会漂移的分类名。）
- **`$#` 不加引号的技巧**：在这条 busybox ash 链路上，`test` 里的 `"$#"` 会被当成注释开头，
  整条 `[ "$#" -eq 0 ]` 判断静默失效（不报错，只会永远为真或永远为假）。
- **只读状态输出是页面与断言共同依赖的对外契约**：每行严格「键=值」、键名固定、返回码恒为 0、
  允许出现多行 `log=`；登录凭据只报有效性（`ok` / `fail` / `none`），明文绝不进输出。
  调试档位是其中一个字段（`debug=`），**页面不自带默认值**——档位一律取自这份输出。
- **分发路径置 `FAFU_MANUAL=1`（不 export）**：`cmd_dispatch_rc` 在调处理函数**之前**，
  在**管道右侧的那个子 shell 里**置上它（处理函数就跑在那里，写到 `cmd_dispatch` 那层看不到）。
  base 层的 `_log_repeat` 认这个标记——人主动按的子命令触发的失败一律算「当日首次」，不受去重限制。
  **绝不能 export**：导出了会被 `enable` 派生的守护进程继承，那个进程会整天不去重。
  （`tests/poll.sh` 专有一条用例把「子进程看到的 `FAFU_MANUAL`」记下来钉住这一点。）

**失败去重（`log_once`，跨层共用）**

- **要解决的是「一晚上同一条原因刷出一百多行」**：拿不到任务或提交失败时，主循环每 60 / 240 秒
  重试一次，同一条原因能一路刷到三小时。去重因此不是「少写日志」，而是把**没有新信息的重试**
  挡在默认档之外——重复轮次本身仍然写，只是写进调试档。
- **口径与既有的两处完全一致**，不引入第三种记法：通知的「当日仅首次」（`notify_once` 的标记）
  与任务变化行的「只在变化时写」。三处都是同一句话——**没有新信息就不打扰**。
- **两个入参都不进日志文案**：`$1` 是失败类别（稳定标识），`$2` 是原因签名。分开的理由是
  「两个不同的故障各留各自的首次」与「同一种失败的原因变了要再留一条」是两件事：
  类别让前者成立，签名让后者成立。签名取「rc + api 层那行稳定事实（`_api_cause`）+ 正文 / 失败档位」，
  于是「网络不通」变成「服务端拒绝」这种**原因变化**会立刻再记一条。
- **`_log_repeat` 的返回码方向别写反**：它是**谓词**——命中「已见过」返回 0（是重复），
  没见过 / 换了原因 / 换了类别 / 跨日 / `FAFU_MANUAL=1` 返回 1（首次）。
  写成「是不是首次」会让 `log_once` 把两档**正好写反**（默认档只留重复的那些）。
- **类别 5 个、调用点 7 处**（类别与调用点不是一一对应，别按「5 个类别 = 5 处」去数）：
  `fetch`（`_sg_fetch_fail` **一个调用点同时管「查询异常」与「获取任务失败」**——事件名不进原因键，
  原因相同的两个失败点共用一个键）、`nold`（未检测到应用数据，原因键固定档 `fixed`）、
  `notask`（暂无有效任务，同样 `fixed`）、`submit`（签到失败汇总行）、
  `ka`（保活失败三档，原因键 = rc + `_api_cause` + **失败档位**：延后 / 冷却中 / 静默刷新
  是三种不同的处置，各算一个原因）。
  **别把它套到降级行上**——`提交尝试` / `不在签到时段` 已由 `logd` 判定，
  两套判据叠在一起会让「这行为什么没出现」变得无法推理。
- **状态只在内存**（shell 变量），不落盘、不动状态层、不新增运行时文件；跨日重新计数，
  守护进程重启后最多重复一行。这是刻意的取舍：为去重落一份盘，等于给一个**只影响可读性**的
  机制加一份新的状态契约，而它失效的最坏后果只是多几行日志。
- **手动命令不受当日去重限制**：分发路径置的 `FAFU_MANUAL=1` 让 `_log_repeat` 一律判「首次」
  （置在哪、为什么不 export 见上面的 commands 层）。理由是频率判据——人主动按的子命令频率由人控制，
  价值就是「我刚按了按钮，发生了什么」，把它的输出静默吞掉才是真的坏。
- **默认档的失败行必须仍然带着接口那次的完整诊断**（`http=` / `body=` / `耗时=` / `hdr=` /
  `net rc=`）。**降级只影响「写不写」，不影响「写什么」**——这条是默认档还能定位故障的前提，
  改 `log_once` 时不要把压平好的事实丢掉一层。原因键那一侧正相反：`_api_cause` 特意**剔掉**
  `hdr={…}` 与 `耗时=…`，那两段是这一次调用的读数、不是原因（见 api 层）。

**四个安装 / 启动脚本与页面**

- `service.sh` / `action.sh` / `customize.sh` / `uninstall.sh` 与 `webroot/index.html`
  本轮逐条核对后没有需要搬走的论证：头块都在 15 行以内且只有「职责 + 关键约束」，
  文件内没有超过 3 行的注释块，正文里没有复述与历史叙事。
- 页面里那几处「看着像复述、实为契约」的短注按不变量原样保留：生效值缺失就显示「没有取到」
  （不代入页面默认值）、分发路径会给以换行收尾的输出补一个空行（故空行一律跳过）、
  `ksu.exec` 的回调参数与显式 `cwd` 的约定、以及「前端这次校验只为止损，脚本侧仍是唯一闸门」。

**三处有意偏离 Miuix，改动时不要「修回去」**：

1. **不复刻 squircle 圆角**，统一 `border-radius:16px`。Miuix 用三次贝塞尔路径
   （`SquircleDefaults.Extension = 1.1`、控制点比 `SQUIRCLE_CONTROL = 0.643`），CSS 无等价物；
   `corner-shape:squircle` 要 Chromium 139+，而管理器 WebView 版本不可控，`clip-path` 又会
   连焦点框与描边一起剪掉。16px 尺度上肉眼差异极小，不值得换这些代价。
2. **不外链也不内嵌字体**：官方 Web demo 用 MiSans 的 CDN，与「零外部引用 + 离线可用」直接冲突；
   内嵌 woff2 会让单文件从 20 多 KB 涨到数百 KB。改用系统字体栈——HyperOS 上 `system-ui`
   本来就解析到 MiSans，「像不像」在这个仓库里靠的是颜色与形状，不是字体文件。
3. **正文行高 1.5**（Miuix `paragraph` 是 1.2em），日志 `pre` 保持 12px 等宽：中文可读性
   与「一屏看更多行」优先于逐字复刻。

**配色只有一处真源**：`:root` 里那组自定义属性，深色在同一处整段覆盖。改配色只改那里，
不要在规则里写死颜色值。两处**不是** Miuix 原值、不要按原值「校正」：`--accent`（生效值文字用的
深一档蓝，为在浅色卡片上过 AA 对比度）与 `--ok` / `--bad`（语义色，Miuix 只给了 `error`）。

**反馈分层的落点**：瞬时进展走底部 `#snack`（3.2 秒自动收，新一轮操作前先收掉上一条，
避免「正在保存…」与结果同屏滞留）；**要留痕的结果走 `#msg` 常驻**——
保存被拒绝的原因、校验失败都属于这一类，做成会消失的浮层等于把
「旧值保持不变」这个关键事实藏起来。落常驻结果统一走 `result()`（先收提示再写 `#msg`），
**别在调用点手写 `hideSnack()` + `note()`**：那样漏一处就是「进度与结果同屏」。
唯一的例外是**桥接不可用**——那时 `#app` 整块是 `hidden` 的，`#msg` 在隐藏容器里看不见，
所以它走自己的 `.banner#nobridge`。

**高级区每次打开都回到折叠态**（`#f_adv` 的 `aria-expanded` + `#adv_panel` 的 `aria-hidden`）：
不做记忆——「上次点开过」会让同一个页面在不同时候长得不一样，而这个差异无法向使用者解释。
折叠用 `max-height` 过渡而不是 `hidden`/`display`：后者没有高度动画可做（spec 要求展开有过渡），
收起时先落一帧当前高度作起点，否则 `0 → N` 与 `N → 0` 都会跳。

### 2.2 运行时行为

**子命令分发与命令表**（`lib/commands.sh`）：

入口只做三件事：认子命令（`cmd_known`，不在表里也不是 `start` → 打印用法并以 1 退出）、
分发（`cmd_dispatch`）、以及「不带子命令 / `start`」时的守护进程启动（入口的 `cmd_start`）。
命令表 `cmd_specs()` 一行一个子命令，四列：**名字 / 处理函数 / 是否需要降权探测 / 一行说明**，
它同时驱动三件事 —— 分发、降权探测集合、用法文本；新增子命令 = 表里加一行 + 写一个
`cmd_<名字>`（`tests/commands.sh` 用一份临时模块副本验证这条，改动仓库文件之外没有第三处要同步）。
表里没有 `start`：它的处理函数就是入口的 `cmd_start`（后台化 + 单实例判定）。
**表当前 11 行**（原 9 条手动排查命令 + 为配置页新增的只读状态输出与写入两条）。

第三列是**两处探测的共同判据**：入口在装配阶段按它决定探不探（`cmd_probe_needed`，`start` 与
不带子命令恒探），`cmd_dispatch` 在没继承到结果时也按它兜底。标 0 的七条因此完全不碰 `su`——
白等一次 `su` 只是代价的一半，另一半是探测会往日志里写一行，而 `webstate` / `status` 的输出里
恰好带着日志尾部（配置页的「最近日志」），读一次状态就会让页面第一条日志变成「通知链路:
降权写法 … 可用」这种与本次操作无关的行。

`cmd_dispatch` 分两趟：第一趟按表把该探测的命令探完（只在主 shell 里跑，`SU_MODE` 才留得住），
第二趟才找处理函数并执行。「探测先于任何分发」因此是结构上的必然，不靠注释或断言维持。
处理函数一律以 `exit` 收尾（分派到哪个子命令，这个进程就只做那一件事），所以它必须在
`{ }` 的子 shell 里被调用——直接调用的话，连回传退出码的那行哨兵都会被它一起带走。

装配阶段还有**同一次降权探测**（入口在分发之前，见「通知」一节的说明）：守护进程是入口派生
出来的后台进程、不在命令表里，不在这里探就会带着空的 `SU_MODE` 常驻，之后它发出的每条通知
都被静默丢弃。它同样由第三列把关（`cmd_probe_needed "$CMD"`）——所以「守护进程必须有写法」
与「只读命令不该白探」这两条要求落在同一个判据上，不必在入口另列一份命令名单。

**为配置页新增的两个子命令**（也在同一张表里，命令表因此是 11 行）：

- **只读状态输出**：无参数，输出一份供页面解析的键值行——服务开关、**守护进程是否在跑**
  （`daemon=running|stopped`，与开关是两个维度：停用而进程还在时照实报 `running`）、今日签到状态与时间、
  今日保活成功 / 失败次数、最近一次保活的时间与结果、登录状态**是否有效**、版本号、**调试档位**
  （`debug=0|1`，放在配置项那一组的末尾）、最近若干条日志。
  **不输出登录凭证明文**（只给有效性）；要看凭证明文仍用 `status`（默认档下它同样打码）。
  页面侧的档位**只取自这个字段**，不自带默认值——页面自己存一份默认值必然与配置层漂移。
  它**不做档位过滤**：无论哪一档都交出同一份字段与同一段日志尾部（级别只作用于写日志文件那一处）。
- **写入**：接收若干「键=值」，作为配置写入的**唯一校验闸门**完成校验、整份落盘，并**回读生效值回显**，
  让页面能确认配置真的进去了；返回码与失败原因对页面可见（页面据此决定是回显新值还是恢复显示旧值）。
  非法值在这里被拒绝、旧值不变——所以页面不可能把一段可执行的 shell 代码写进模块。
  `DEBUG` 走的就是这一条：配置页保存分支把它按 `'1'` / `'0'` 交给闸门，与其余开关项**同一形状**。

两个子命令的**本质区别是权限面**：只读那条不改变任何状态，写入那条是唯一能改配置文件的路径。
页面侧只经这两条命令与既有的启用 / 停用子命令操作模块，不直接读写任何文件。

**`status` 的「开关」与「守护进程」是两套判据**：前者读状态文件（意愿），后者读 PID + cmdline（实况）。
两者矛盾（开关启用、进程不在）时 `status` 多打一行 ⚠️ 说清后果与恢复办法，页面用同一条提示、
数据取自 `daemon=`。这是给「开关看着是开的、其实早就没进程」那个状态加的可观测性，不改变行为。

命令分发把子命令之后的参数**原样**交给处理函数（处理函数因此要能收参），这是本次唯一改动
分发核心的地方——对应的记录桩生成方式与逐字断言一起更新。

**分发不依赖任何外部 fd**（这两条都是设备实测换来的）：

- 处理函数的输出与返回码必须分开走，现在的做法是**一层命令替换 + 一行哨兵**：
  `rc=$( { "$handler"; echo "$CD_SENTINEL$?"; } )` —— 输出在前、哨兵行在末尾，
  调用方剥掉哨兵即得返回码，全程只用 fd 1。
- 先前用 fd 3 承接输出，这是错的：fd 3 是**调用者的环境事实**，管理器的 WebUI shell 与
  交互式 root 终端常常是关着 fd 3 exec 本脚本的，而这类 shell 下「重定向一个未打开的 fd」
  是**致命错误**（脚本当场以 1 退出，`||` 兜底都执行不到），四条手动命令会一起废掉。
  「先探测 fd 3 可不可用、不可用就丢弃输出」这条路同样走不通（探测本身就是那次致命重定向），
  只能从机制上不依赖它。

**守护循环**（60 秒一跳，按当前时间分流）：

- **轮询范围内**（`POLL_START` ~ `POLL_END`，默认 20:00 ~ 23:59）：查任务 → 未签则提交；
  成功后写当日完成标记（`run_once` 返回 2 时 4 分钟后重试；每分钟循环天然重试）。
  **当日已解决**（签到成功 / 补签成功 / 检测到已在 App 内签到 / 今日请假，见
  `state` 层的 `signin_resolved_today`）就不再查看任务——「今晚的事办完就不再反复查询」，
  这一条取代了原先按钟点收工的写法。三条截止提醒与「任务还没发布」的兜底提醒都在这一支里发。
- **保活时段**（`KA_START` ~ `KA_END`，默认 07:00 ~ 21:25，**上界不含**）：每 15 分钟一次。
  窗口与节流都由 keepalive 层判定（`ka_in_window` / `ka_due`，入口只按结论分流），
  入口不再内联时点与间隔。这一支与「轮询范围内」是**并列**的：当日是否已解决只挡查看任务，
  不挡保活（签到办完了 token 照样要续期）。
- 两个窗口端点都来自配置层，写法（范围、先后）由 `cfg_write` 的闸门校验；其余时间空转

**守护进程的存活边界（#30）**：从管理器页面（WebUI 的 `ksu.exec`）起的进程，继承的是
管理器 App 的 **cgroup 与进程组**。管理器一关，Android 会把那个 cgroup 连同里面的进程
一起回收——进程被 SIGKILL，**日志里不会有任何退出行**，`status` 只会看到「未运行」。
开机脚本由 init 拉起，不在 App 的 cgroup 里，所以「开机起的一直好用、页面起的一关就没」
不是签到链路的毛病，而是启动上下文的差别。

两道处理都由入口与 base 层承担：

- `spawn_detached`（base）：优先 `setsid`（= 新会话 + 新进程组），再用 `nohup` 忽略挂断；
  两者都没有时退回普通后台。管理器回收自己的进程组时因此带不走守护进程。
- `cgroup_escape`（base，守护进程启动后的第一件事）：照 ksud 的 `switch_cgroups`，把自身
  PID 写进 `/sys/fs/cgroup`、`/dev/memcg/apps`、`/acct`、`/dev/cg2_bpf` 各层的
  `cgroup.procs`。清单里**第一个存在**的层级是主层级（v2 设备是 `/sys/fs/cgroup`，旧设备
  是 `/dev/memcg/apps`），它写不进去就算失败，日志留一行「未能离开管理器 cgroup」；
  不在 App cgroup 里（开机路径）返回 2，什么都不做、也不写日志。

KernelSU 侧的证据：WebUI 的 `ksu.exec` 走 `ksud debug su` → `grant_root()`，这条路径不调
`switch_cgroups()`；`su -c`（`root_shell()`）与模块「操作」按钮（`exec_script_with()`）
都会调。故上游即便某天补上，模块自己也留这道兜底。`tests/daemon-detach.sh` 用假 cgroup 树
钉住迁移，并在 Linux 上用 `ps -o sid` 钉住「守护进程 = 新会话首进程」（Windows 上跳过）。

**保活**（`keepalive_ping`）：

1. 调用 `sign_in/student/my/page`（rows=1）——成功即续期
2. 失败时：**熄屏** → 立即静默刷新（30 分钟冷却）；**亮屏** → 延后
   （等熄屏，或进入轮询范围后由签到流程处理）
3. 每次结果都经 state 层的 `ka_note` 落统计，日志一行同时带上「今日成功 / 失败」两个数

**刷新**（`refresh_token`）：流程按三段组织，一段一个取舍，页面与屏幕动作各归其段。
第三个参数是**触发原因**（`签到查询失败` / `签到提交失败` / `保活` / `手动命令`），它只进日志、
不改变任何时序——日志里出现刷新时，读的人得知道这一次是谁触发的。

1. **`refresh_silent`（静默开页等 token）**：屏幕已亮时先发预警并留出阅读时间，
   再打开打卡页（熄屏下屏幕不亮）；随后每 3 秒采样一次 leveldb，最多 10 次
2. **`refresh_wake`（唤醒后重试）**：静默段拿不到才走这里——屏幕原本没亮时
   `input keyevent 224` 唤醒、`wm dismiss-keyguard` 解锁，再采样最多 20 次；
   **保活场景由调用方传 0 禁止唤醒**（`refresh_token "$tok" 0 "保活"`），避免白天吵醒用户
3. **`refresh_finish`（收尾）**：`am stack remove` 清理页面任务（清理不彻底就留在后台，
   **不**主动切换用户前台；见 §2.1.1），再把屏幕恢复成刷新前的样子（原为关闭就恢复熄屏）

两条时序不变量**跨段**成立：拿到新 token 后由 `refresh_token` 就地提前关页（前台尽早交还
用户），拿不到则不提前关页（走完第二段再一起关）。`tests/keepalive.sh` 用真实设备命令替身
数「关了几次页」来钉住这两条。窗口、节流、保活四态同样在该套件里用拨钟覆盖。

**动态描述**（`desc_text` / `update_desc`，均在 `lib/desc.sh`）：

- 内容：开关状态 + 签到日期时间（绝对日期，如 `🟢 已启用 · ✅ 09-14 已签到 21:30`）；
  数据只经 state 层读（开关 + 最近签到记录），本层不碰任何文件格式
- 写入：KernelSU 用 `ksud module config set override.description`（官方机制）；
  Magisk 回退为改写 `module.prop`——改写前必须校验临时文件非空，
  否则一次失败的读取会把模块元数据清空（管理器里连模块名都没了）
- 触发：检测到已签到 / 已请假、签到或补签成功（`signin` 层）／启用、停用、`status`（`commands` 层）／
  服务启动、已停用退出前、守护每约 10 分钟自检（入口）；调用点共 8 处，由 `tests/state.sh` 的
  「desc · 触发点」钉住

**服务开关**：状态文件 `fafu-checkin.state`（`enabled` / `disabled`）。
停用 = 停进程 + 开机不启动 + 无网络请求。

**通知**（`notify_event` / `notify_once` / `notify_warn`，模板见 `_msg_*`，tag 见 `tag_of`）：

- 触发：签到成功 / 补签成功 / 检测到已签到 / 检测到请假 / **当日首次**签到失败 /
  **当日首次**获取任务失败 / 三条截止提醒（主窗口还剩 30 分钟、进入补签时段、补签截止，
  三个时刻都由服务端任务数据推算，文案里的钟点随之生成）/ 到 `min(轮询范围止, 23:00)`
  仍未取得任务的兜底提醒（挂本地时钟，与轮询窗口无关）/ 打开打卡页前的预警
  （屏幕已亮时必发，与静默路径或兜底唤醒无关）
- 去重：失败类与未签提醒用标记文件做「一日一次」（失败类的两个事件名共用一个标记）；
  同 tag 的通知相互覆盖（同日同事件不会堆积）
- 预警条件：**屏幕已亮**（本次确实会打开打卡页）且距上次打扰型通知超过 `NOTIFY_COOLDOWN`（默认 300 秒）
  才发，且排在 `open_page` **之前**，并 `sleep NOTIFY_LEAD` 留出阅读时间；
  熄屏时**不发**任何预警——那条路径是静默开页（屏幕不亮），用户看不见，发了也无意义。
  排查历史：最初只把预警挂在「兜底唤醒」分支上，结果**屏幕亮着走静默路径开页时漏报**
  （设备实测发现），故改为按「屏幕已亮 + 即将开页」判定，与走哪条路径无关；
- 机制约束与坑见 §2.1.1

### 2.3 运行时文件（均在模块目录内）

除日志、PID 文件与 api 层的三个旁路文件外，下表 state 层那批文件的读写都收口在 `lib/state.sh`
（见 §2.1 的层结构约定）：其余层只经它的语义函数访问，不直接碰文件。

`fafu-checkin.conf` 与它们**不同类**，单列在表首：它是使用者拥有的**配置**，由 config 层读写；
下面那批是模块自己的**运行时状态**（当日有效、可被丢弃重建），由 state 层读写。
两者的生命周期也不同：模块升级替换的是模块自身的文件，配置文件不在包内、也没有脚本删它；
运行时状态是否随升级重置，**以真机实测的管理器行为为准**（本机无法验证这一点）。

| 文件 | 内容 | 写入者 |
|---|---|---|
| `fafu-checkin.conf` | **配置**：键 = 值若干行（键登记与默认值见 `lib/config.sh`）。唯一一个**由使用者拥有**、且由 config 层写入的文件；升级模块时它代表使用者的一面，不随运行时状态一起被当作可丢弃物 | config 层（写入闸门整份原子重写） |
| `fafu_checkin.log` | 日志（超 256KB 自动保留最近 1000 行）。**档位只作用于这一处**：默认档留结果与原因，调试档另加写回完整现场的那些行；轮转与保留策略不随档位变化，故一直开着调试档也不会无限增长。全程序只有 base 层的 `_log_write` 一个落地点 | base 层 `_log_write`（经 `log` / `logd` / `log_once` 三个出口，档位判定只在后两个） / `rotate_log` |
| `.fafu_checkin.pid` | 守护进程 PID | 入口 |

| `fafu_keepalive.status` | 保活统计（今日成功/失败、最近 token）。**这里那份 token 是明文，且保持不动**——它是运行时状态、被当值取用（打码会直接写坏统计），不受 `DEBUG` 与显示层打码影响 | state 层 `ka_note` |
| `.fafu_checkin_done` | 当日签到完成标记 | state 层 `done_mark` |
| `.fafu_notify_fail` | 当日「失败类通知」已发标记（`notify_once` 去重） | state 层 `notify_mark fail` |
| `.fafu_notify_nosign` / `.fafu_notify_late` / `.fafu_notify_miss` | 三条截止提醒各自的已发标记（时刻由任务数据推算，与具体钟点无关） | state 层 `notify_mark nosign` / `late` / `miss` |
| `.fafu_task_seen` | 当日「已取得任务」标记。它同时是「任务未发布」兜底提醒的已发标记：真的取到任务、或已经为此提醒过，任一成立都表示今天不必再打扰 | state 层 `task_seen_mark` / `notify_mark nopub` |
| `.fafu_task_snap` | 任务快照：最近一轮拿到的任务号 / 签到状态 / 开始 / 截止（外加写入当天的日期键）。四元组任一变化才写一行「任务变化」；日期不是今天即视为「没有快照」，故跨日不会拿昨天的任务当基准 | state 层 `task_snap_get` / `task_snap_set` |
| `.fafu_notify_last` | 预警通知冷却基准（unix 秒；必须落盘，见 §2.1.1） | state 层 `nt_cooldown` |

接口层另有三个**自己管**的旁路文件（不属状态，由 api 层独占，字段含义见 §3.5）。
它们**不是日志**：`DEBUG` 只作用于「往 `fafu_checkin.log` 写行」这一处，
所以默认档下最后一次调用的完整事实仍然留在 `.fafu_api.err` 里，排查时该看还看得见。

| 文件 | 内容 | 写入者 |
|---|---|---|
| `.fafu_api.err` | 接口诊断行：每次网络调用**恰好一行**（`http=` / `body=` / `bodylen=`+`trunc=` / `hdr=` / `耗时=`；连接层失败是 `net rc=` + `http=-` + `err=`） | api 层 `_api_note` |
| `.fafu_api.hdr` | curl `-D` 的响应头原文（整包头；日志只从里面挑白名单四项） | curl（落点由 api 层给） |
| `.fafu_api.raw` | 网络工具的 stderr 原文（可能多行；只有首行经 `err=` 进日志） | curl / wget |

## 三、调试手册（已知坑）

### 3.1 系统命令必须重定向（KernelSU 特有问题）

`am` / `dumpsys` / `input` / `wm` 通过 binder 传递自身 fd，KernelSU 的 SELinux 策略会拒绝
向 `/data/adb` 下文件传递 → 命令报 `Failed transaction (2147483646)`。

**规则**：每一个系统命令调用点都固定 `</dev/null`（stdin 接死），再按用途决定另外两个——
不需要输出的（`am start` / `am stack remove`）连 stdout 一起丢 `>/dev/null 2>&1`；
需要读输出的（`_dumpsys`）保留 stdout、只丢 stderr。由此得到的不变量是
**命令自身的 fd 永远不流进 `/data/adb`**；至于命令的输出去哪，两种都合法——
经变量承接（`screen_is_on` 的 `out=$(_dumpsys power)`），或就地接管道
（`_activity_records` 的 `_dumpsys activity activities | grep … | sort -u`）。
判据在 `tests/device.sh`：`am` 命令位 3 处、`dumpsys` 命令位 1 处，逐处带 `</dev/null`；
替身还会在「某个 fd 接到普通文件」时报红。

### 3.2 网络工具（curl 优先，busybox wget 兜底）

- **失败时两个工具的能力不一样**，这是选 curl 的唯一理由：
  - `busybox wget`：4xx/5xx **不输出响应体**，stderr 只有一句
    `wget: server returned error: HTTP/1.1 403`（没有服务端的 `message`）
  - `curl`：`-w '\n%{http_code}'` 能同时拿到**响应体与状态码**，服务端的结构化报错
    （`{"status":400,"error":"…","message":"…","path":"…"}`）因此可读
- api 层加载时探测一次 curl（`CURL_BIN`）。候选自上而下逐个试：
  `command -v curl`（PATH 上的，终端里常由管理器挂进来）→ `/data/adb/curl`（想固定用某一份时放这里）
  → `$MODDIR/curl` → `/system/bin/curl` → `/system/xbin/curl`。**认「能跑」不认「文件在」**：
  `[ -x ]` 只证明文件存在，故每个候选都要真的跑一次 `--version` 并看退出码，
  「存在但起不来」的 curl 不算可用；探测与调用都清掉 `LD_LIBRARY_PATH`。
  一个都没有时回落 wget。要强制走兜底路径：在模块目录建 `.fafu_no_curl`
  （排查用；测试也用它钉住两条路径）
- 判定的语义：**调用方只看返回码**（0=成功 / 非 0=失败），不 grep 响应体；而返回码本身由工具路径
  决定——**curl 路径下 2xx 才算成功**（4xx/5xx 也算失败，否则服务端的报错正文会被当成正常响应体
  交出去），**wget 兜底路径沿用工具的退出码**。两条路径的返回码语义因此不完全相同，
  上层不必也不该自己解析响应体去补判
- **兜底路径也能给出状态码与响应头**：没有可用 curl 时用 busybox wget，加 `-S`
  （显示服务端响应）后它会把状态行与响应头（每行缩进两格）写到 stderr，状态码与白名单四项
  从那里取，于是这一档的日志**与 curl 同形**；工具没吐响应（连不上 / 该构建不吐）时才回落
  `net rc=<退出码> http=-`——不拿退出码冒充状态码
- 请求由 `http_post()` 统一发出（全程序唯一的网络出口，`-T` 是 wget 侧的编译开关，
  不支持则整段省略）。它把**这一次调用的全部事实**写成 `$API_ERRLOG`（模块目录
  `.fafu_api.err`）里**恰好一行**（每次调用先清空，故文件里只有这一次的），两档形态：
  - 拿得到状态码（curl 路径，成功与被服务端拒绝**同形**；wget 兜底路径吐了状态行时也一样）：
    `http=<码> body=<完整正文> [bodylen=<原始字节数> trunc=1] [err=<工具原话>] [hdr={…}] 耗时=<N>ms`
  - 拿不到状态码（curl 连不上 / 超时，或 wget 没吐响应）：
    `net rc=<工具退出码> http=- [body=…] [err=<工具原话>] [hdr={…}] 耗时=<N>ms`
  上层一律用 `_api_err1 "$API_ERRLOG"` **原样转交**这一行，不自己拼 `http=` / `body=` /
  `hdr=` / `耗时=`，也不再各自 `head -c` 截断；要用那一行里的响应头（`Date`）时用只读访问器
  `_api_hdrs`，仍然不自己拼 `hdr=`。`api()` 只在**失败时**把这一行转交 stderr
  （返回码语义不变），成功时静静留在文件里备查。
  **失败原因只能这样收**：只留状态码的话，「服务端拒绝 / 连接失败 / 超时」在正文为空时
  仍然分不出来；而由调用方重定向 stderr 去收，会把 `set -x` 追踪与子命令提示行一起收进来
  （首行可能是 `+ local url`）。
- 响应头原文与工具 stderr 原文各有一个旁路文件（`.fafu_api.hdr` / `.fafu_api.raw`），
  日志行只从它们里面挑白名单四项与**报错那一句**（wget 加 `-S` 之后 stderr 首行是状态行，
  故报错按 `wget:` 前缀取，不再按首行取）。每个字段各自用来判断什么、三层证据链
  怎么读，见 §3.5

### 3.3 其他坑（都已在代码中修复，改动时注意保持）

### 3.4 排查入口

```sh
M=/data/adb/modules/fafu-checkin
cat $M/fafu_checkin.log            # 全量日志（默认档只留结果与原因）
sh $M/fafu_checkin.sh setconfig DEBUG=1   # 要看完整现场时先开调试档（改完记得关回去）
sh $M/fafu_checkin.sh status       # 开关/守护进程/保活/token 一览（token 默认打码）
sh $M/fafu_checkin.sh notify       # 发一条测试通知（确认通知链路是否真的能送到）
sh $M/fafu_checkin.sh keepalive    # 手动保活（直接看 token 是否有效）
sh $M/fafu_checkin.sh once         # 手动签到检查（幂等）
```

> 排查前先想清楚要看哪一档：**默认档留的是「结果与原因」**（签到结果、失败原因、通知异常、
> 每日一次的任务与时间核对，失败带完整诊断）；**逐次现场在调试档**
> （`提交尝试:`、`不在签到时段`、保活心跳、页面收尾检查、降权探测「可用」那一行）。
> 两档文案逐字一致，所以下面按字段读的方法在任一档都成立（逐行归属见 §3.5）。

日志关键行：`✅ 签到成功 [晚查寝签到]` / `签到失败: rc=…` / `查询异常: rc=…` /
`保活: ✅ 静默刷新成功 <旧> → <新>` / `保活: ❌ <token> 调用失败 rc=…`。
（保活心跳 `保活: ✅ <token> token 有效` 在调试档；默认档看 `status` 的今日成功 / 失败数与最近一次结果。）

**签到提交的每一次尝试都单独记一行**（一天只有一次现场，事后再补字段要等一天）——
**这些尝试行在调试档**；默认档由结果行（`✅ 签到成功` / `签到失败:`）承载同一批事实。
字段逐条的判读方式见 §3.5，这里只看形状（下面几行都是真实产物，来源与复现方式见 §3.5 末尾）：

```
提交尝试: try=1 rid=88123 lng=119.243462 lat=26.088417 http=400 body={"timestamp":1759500000000,"status":500,"msg":"busy"} hdr={Date: Mon, 13 Oct 2025 21:30:00 GMT|…} 耗时=1224ms
提交尝试: try=1 rid=88123 lng=119.243462 lat=26.088417 http=200 body={"code":0,"msg":"success"} hdr={Date: Mon, 13 Oct 2025 21:30:00 GMT|…} 耗时=1076ms
✅ 签到成功 [晚查寝签到]
签到失败: rc=1 rid=88123 lng=119.243462 lat=26.088417 try=4 tries=2 http=400 body={"timestamp":1759500000000,…} hdr={…} 耗时=1001ms
```

- 事件名只有一个 `提交尝试:`（成功与被拒**同形**，只差状态码与正文），失败与成功逐字对比
  因此成立；每次尝试各自一行，最后一次失败的尝试也有自己那一行；
- 全部尝试都失败时另有一行 `签到失败:` 汇总——它只补「总共试了几次」（`try=`）与短重试次数
  （`tries=`），服务端原文同样原样转交，本层不再截断；
- 判定类别看这里：403/401 = 服务端不认这次提交；500/503 = 服务端故障；
  无状态码而只有连接类文案（`net rc=`/`err=`）= 网络层；`body` 里那句 `message`
  才是服务端给的原因（它现在**完整**落在日志里，不再被截在 200 / 300 字节处）。

### 3.5 排障日志字段对照（每个字段用来判断什么）

签到每天只有一次窗口，一次失败要再等一天才有下一个现场。所以日志的目标不是「记得多」，
而是**一次现场就能定性**：把服务端与本地两侧的事实并排放在同一行里。

**两档日志与逐行归属**（先看这一节，再看字段；字段表在两档下都成立）

只有两档，由配置键 `DEBUG` 决定：**默认档**（`DEBUG=0`，出厂设置）与**调试档**（`DEBUG=1`）。
**行格式完全不变**——行首时间戳 + 文案，不引入级别前缀或标记；**两个档位的文案逐字一致**，
区别只是某些行可见与不可见。所以下面按字段查日志的读法不会因为档位不同而失效。

判据只有一条，以后新增日志时照它归属，不必重新开会决定：

> **频率 × 信息量**——**分钟级重复且内容不变的行降级到调试档；每日一两次的、即使偏诊断也留在默认档。**

降到调试档的行共 **7 条**（**按文案识别，不认行号**——重构搬动代码不会让这份归属失效）：

| # | 层 | 文案锚点（完整文案见右列说明） | 为什么降 |
|---|---|---|---|
| 1 | signin | `应用数据暂不可读（重启后就绪前的瞬时状态？），最多等 N 秒` | 只在重启后的瞬时等待里出现，等不到会另有一行结论（见 #2 与「未检测到应用数据」） |
| 2 | signin | `应用数据已就绪（等了 N 秒）` | 与 #1 成对的头尾两行，必须同降同留 |
| 3 | signin | `[任务名] 不在签到时段` | 窗口内每分钟一条、结论不变，正是「一天几百行」的主来源 |
| 4 | signin | `提交尝试: try=N rid=… lng=… lat=… <api 层事实>` | 每次提交（含短重试）各一条；它承载的事实**已原样并进**结果行与失败行 |
| 5 | device | `页面关闭检查: 残留活动=N` | 每次关页一条，正常时恒为 0；**真残留**时另有「页面移除未彻底」留在默认档 |
| 6 | notify | `通知链路: 降权写法 [写法] 可用（id -u = 2000）` | 每次启动探测一次、结论不变；失败路径（`找不到 su` / `降权不可用`）留在默认档 |
| 7 | keepalive | `保活: ✅ <token> token 有效 (今日 N 成功 / N 失败)` | 每 15 分钟一条心跳；成功次数在运行状态与 `status` 里已经有了 |

**留在默认档的行**（按类别，不逐条列全）：**「留在默认档」= 这一行不加任何档位判定**
（照旧走 `log`，两档都写），判据的正面则是「每日一两次 × 解释使用者看得见的行为」。

- **入口**：`服务启动`、`已有实例(PID N)在运行，退出`、`检测到服务已停用，守护进程退出`；
  以及入口那条 `模块不完整：缺少库层 <路径>`——它**不走统一日志出口**（那一刻库层还没加载），
  因此天然不受级别影响，**不要动它**。
- **base**：`日志已轮转（保留最近 1000 行）`。
- **命令层**：全部手动子命令的行——它们的频率由人控制，价值就是「我刚按了按钮，发生了什么」
  （`手动刷新测试` / `手动保活检查` / `无 token` / `token 有效` / `调用未成功` /
  `刷新成功` / `新 token 接口验证通过` / `新 token 接口验证异常` / `刷新失败` /
  `守护进程已停止` / `服务已启用` / `服务已停用`）。
- **签到层**：`任务变化: …`（本来就只在四元组变化时写）、`时间核对: …`（每日一次）、以及**全部结果行**
  （`[任务名] 已签到` / `[任务名] 已请假` / `提交重试 N 次后成功 [任务名]` /
  `✅ 补签成功 [任务名]` / `✅ 签到成功 [任务名]`）；失败类另见下面的去重。
- **保活层**：`刷新 token（静默优先）`、`静默刷新未成功，尝试唤醒屏幕重试`、`屏幕原为关闭，已恢复熄屏` /
  `屏幕原本亮着，保持不熄屏`、`已取得新 token，提前移除打卡页`、`刷新成功:` / `刷新未获得新 token`、
  保活失败三档（`保活: ❌ … 调用失败 rc=…` / `保活: ⚠️ … 调用失败 rc=…`，**走当日去重**、
  见下面「默认档的失败去重」）、
  `保活: ✅ 静默刷新成功` / `保活: ❌ 静默刷新未成功` ——它们解释的是**使用者看得见的行为**
  （屏幕亮过、页面弹过）。注意降级的是**心跳**那一条（`保活: ✅ … token 有效`），
  **别按 `保活: ✅` 前缀一刀切**：留在默认档的还有 `保活: ✅ 静默刷新成功`，它每次都写、不去重。
- **通知层**：`找不到 su`、`降权不可用`、`通知发送失败`。
- **设备层**：`页面移除未彻底(残留N)，保留在后台`（只在真残留时写）。

**默认档的失败去重**：同一种失败**当日只写首次，原因变化时再写一次**，重复轮次降级到调试档。
**类别 5 个、调用点 7 处**（`log_once`；类别与调用点不是一一对应）：

| 类别 | 文案锚点（哪一行） | 原因键 | 层 / 位置 |
|---|---|---|---|
| `fetch` | `查询异常:` 与 `获取任务失败:` **共用一处** | rc + `_api_cause` + 本层那份正文 | signin `_sg_fetch_fail` |
| `nold` | `未检测到应用数据（…）——稍后自动重试` | 固定档 `fixed`（没有更细的原因可分） | signin `signin_fetch` |
| `notask` | `暂无有效任务（信息不完整）` | 固定档 `fixed`（缺哪个字段都一样要重试） | signin `signin_parse` |
| `submit` | `签到失败: rc=…` 汇总行 | rc + `_api_cause` | signin `signin_submit` |
| `ka` | 保活失败三档（`保活: ❌ … 延后` / `保活: ❌ … 冷却中` / `保活: ⚠️ … 尝试静默刷新`） | rc + `_api_cause` + **失败档位** | keepalive `keepalive_ping`，**三处调用点** |

- 两个入参（失败类别与原因签名）都**不进文案**，只参与比较；`fetch` 的**事件名也不进原因键**
  ——原因相同时「查询失败」与「刷新后重试仍失败」是同一条失败的两个失败点，默认档只留先到的那条。
- 原因键里的 `_api_cause` **特意剔掉 `hdr={…}` 与 `耗时=…`**（见 api 层）：`Date` 每轮都不同，
  算进原因等于每条都算新原因、去重直接失效。**失败行本身仍带完整的 `hdr=` 与 `耗时=`**。
- 去重状态**只在内存**（base 层的 `_LOG_SEEN`，跨日重新计数），不落盘、不动状态层、
  不新增运行时文件；守护进程重启后最多重复一行。
- **手动命令触发的失败不受当日去重限制**（分发路径置 `FAFU_MANUAL=1`，不 export）；
  **`log_once` 不要套到已降级的行上**（`提交尝试` / `不在签到时段` 已由 `logd` 判定）。
  （取舍得失见 §2.1.2 的「失败去重」。）

**级别的作用范围**：**只作用于「写日志文件」这一处**。只读状态输出的日志尾部、页面显示的最近几条日志、
`status` 的最近日志，都不做级别过滤；**接口层的三个旁路文件**（`.fafu_api.err` / `.fafu_api.hdr` /
`.fafu_api.raw`，见 §2.3）**不是日志**，不受档位影响——默认档下最后一次调用的完整事实仍然留在那里。
`token` 的可见度是**另一个键的同一份判定**：`DEBUG=0` 打码、`DEBUG=1` 明文（见下）。

**三层证据链**（缺一层就只能猜）：

| 层 | 日志里的东西 | 回答什么 |
|---|---|---|
| 服务端说了什么 | `http=`、`body=`、`bodylen=`+`trunc=`、`hdr={…}`（尤其 `Date`）、`记录=`+`记录len=`+`记录trunc=` | 它认不认这次请求、给的原因是什么、它认为现在几点、响应是不是被网关改写或本来就是空的、那条签到记录有没有被我们截断 |
| 我们发了什么 | `rid=` / `lng=` / `lat=`、查询的 `params=`、`try=` | 被拒的那一份参数长什么样、查的是哪一页、这是第几次尝试 |
| 本地环境是什么 | 行首时间戳、`now=` / `TZ=` / `LDP=` | 设备此刻几点、这次的换算发生在什么时区与库路径下 |

三者并排之后，「时间偏差归谁」不必再推理：服务端的 `Date` 与本地 `now=` 同时出现在
日志里，本地时钟偏了还是窗口没开一眼可辨。

**逐字段**（每条给一行真实日志；`…` 表示同行里省略的其它字段）：

- **`http=`**：服务端状态码——判断「它到底有没有收到、认不认」。`401/403` = 不认这次请求
  （登录态或签名），`5xx` = 服务端自己故障；具体原因要看正文里那句 `message`。
  ```
  提交尝试: try=1 rid=88123 lng=119.243462 lat=26.088417 http=400 body={"timestamp":1759500000000,"status":500,"msg":"busy"} hdr={Date: Mon, 13 Oct 2025 21:30:00 GMT|Content-Length: 53|Content-Type: application/json;charset=UTF-8|Server: nginx} 耗时=1224ms
  ```
- **`body=`**：服务端原文，**完整**落盘（不再截 200 / 300 字节）——判断「它给的原因是什么」。
  形如 `{"status":400,…,"message":"…"}` 的那句 `message` 常常正好落在旧截断位置之后。
  ```
  提交尝试: try=1 rid=88123 lng=119.243462 lat=26.088417 http=200 body={"code":0,"msg":"success"} hdr={Date: Mon, 13 Oct 2025 21:30:00 GMT|Content-Length: 53|Content-Type: application/json;charset=UTF-8|Server: nginx} 耗时=1076ms
  ```
- **`bodylen=` + `trunc=`**：正文超过 2KB 时才出现，标出**原始字节数**——判断「这是被我们截断的，
  不是服务端只回了这么多」。两个字段都只在越界那一档出现，正好 2048 字节不截。
  ```
  http=200 body=dddd…（前 2048 字节逐字节原样，此处按长度省略中段）… bodylen=2500 trunc=1 耗时=685ms
  ```
  （这条来自 `tests/api.sh` 的响应体上限用例；`耗时=` 是那次跑出的读数，随机器快慢变化。）
- **`hdr={…}`**：响应头白名单四项（`Date` / `Content-Length` / `Content-Type` / `Server`），
  顺序固定——判断「响应有没有被网关改写、正文是不是本来就是空的、服务端认为现在几点」。
  服务端没给的那项不出现；四项都没有时整段不出现。它由 api 层从**这一次调用的响应头**里挑出，
  并**原样接在需要它的行上**：`提交尝试:` / `签到失败:` / `查询异常:` 这些行接的是 api 层那一行，
  `任务变化:` 与 `时间核对:` 两行则由只读访问器 `_api_hdrs` 把同一段字面量接到行尾
  （上层不自己拼 `hdr=`，格式仍只有一个真源）。**`_api_hdrs` 与失败原因键 `_api_cause`
  共用 `_api_part` 那一套末尾锚定判据**（从最后一次出现处认、尾巴收在 `}` 才算一段），
  所以「并上展示行的响应头」与「去重认的原因」是同一段真读数，不会各自截错。
  ```
  任务变化: id=→88123 state=→0 begin=→1790853600000 截止=→1790859600000 hdr={Date: Mon, 13 Oct 2025 21:30:00 GMT|Content-Length: 53|Content-Type: application/json;charset=UTF-8|Server: nginx}
  ```
- **`耗时=`**：这一次调用花了多久，值自带单位（`ms` / `s`）——判断「是窗口刚开那几秒服务端
  还没开始收，还是它一直不理我」。同一行里，它与 `http=` 一起决定「值不值得再试」。
  读数有**三级**来源：① `date +%s%3N`（毫秒；`%N` 是 busybox 的**可选特性**，没编进去时
  `date` 会把 `%3N` 原样吐出来、数字串里因此多一个 `3`，故只认「≥13 位」并截前 13 位）；
  ② `$API_UPTIME`（默认 `/proc/uptime`）——Android/Linux 一定有，两位小数＝10 毫秒精度，
  为与 ① 共用「13 位＝毫秒」而左补零到 13 位；③ 两者都拿不到（非 Linux 上又恰好没编 `%N`）时
  用 `date +%s`——**10 位读数、单位按秒**。`_api_cost` 只按位数判单位、不认来源。
  看到 `耗时=0s` 这种整秒读数，说明这台设备走到了第三级——不是「调用瞬间返回」。
  三级来源的取舍见 §2.1.2 的 api 层。
  ```
  保活: ❌ 2_C0DE 调用失败 rc=7 screen=on net rc=7 http=- err=curl: (7) Failed to connect to stuhtapi.fafu.edu.cn port 80: Connection refused 耗时=1175ms (今日 0 成功 / 1 失败) — 屏幕亮着，延后（熄屏或签到时段自动刷新）
  ```
  （这条来自保活套件的**调试档**夹具，所以 token 是明文；同一行在默认档里是
  `保活: ❌ 2_****a1b2 调用失败 …`——文案与字段完全一致，只有 token 那一格不同。）
- **`net rc=` + `err=`**：连接层失败那一档的**工具退出码**与**原话**，此时**没有状态码**
  （写 `http=-`，不拿 `000` 冒充）——判断「连不上（DNS / 连接被拒 / 超时）」与「服务端拒绝」
  两件完全不同的事；`rc=7` 是连接被拒、`rc=28` 是超时（curl 口径）。
  ```
  查询异常: rc=7 net rc=7 http=- err=curl: (7) Failed to connect to stuhtapi.fafu.edu.cn port 80: Connection refused 耗时=1072ms params=rows=3&pageNum=1
  ```
- **`try=`**：这是第几次提交尝试（`1` 首发 / `2` 刷新登录态后那次 / `3+` 短重试）——判断
  「第几次才成功」「失败与成功之间差在哪」；`签到失败:` 汇总行里的 `try=` 则是**总次数**。
  ```
  提交尝试: try=1 rid=88123 lng=119.243462 lat=26.088417 http=200 body={"code":0,"msg":"success"} hdr={Date: Mon, 13 Oct 2025 21:30:00 GMT|Content-Length: 53|Content-Type: application/json;charset=UTF-8|Server: nginx} 耗时=1076ms
  ```
  > **这一行在默认档不出现**（见上面的逐行归属）；它承载的事实已原样并进 `签到成功` /
  > `签到失败` 那些结果行，所以在默认档按下面的字段读结果行即可，不必先打开调试档。
- **`触发原因=`**：token 刷新那几行（`刷新 token（静默优先）` / `刷新成功:` / `刷新未获得新 token`）
  都带着它——判断**这次刷新是被谁触发的**：`签到查询失败` / `签到提交失败` / `保活` / `手动命令`
  （调用点不给时写 `未说明`，不留空字段）。异常路径触发的刷新因此不再与正常保活混在一起。
  ```
  刷新 token（静默优先） 触发原因=保活
  刷新成功: 2_C0DE → 2_BEEF 触发原因=手动命令
  ```
- **`任务变化:`**：任务四元组（任务号 / 签到状态 / 开始 / 截止）任一变化时记一行，旧值在前
  新值在后——判断「今晚的任务什么时候出现的、什么时候变的」。跨日后快照按日滚动，同样的任务
  会重新算作「新任务」（旧值为空），而不是被误读成「没变化」；行尾并排这一次查询的响应头，
  于是「任务出现的那一刻服务端认为几点」也在同一行里。
  ```
  任务变化: id=→88123 state=→0 begin=→1790853600000 截止=→1790859600000 hdr={Date: Mon, 13 Oct 2025 21:30:00 GMT|Content-Length: 53|Content-Type: application/json;charset=UTF-8|Server: nginx}
  ```
- **已签到那行**（`时间核对:`，检测到已在 App 内手动签到时写）：整条服务端记录 + 四种时间并排
  ——判断「描述里的签到钟点为什么不对」：`signTime` 是服务端原始毫秒戳、`sign_time` 是按本地
  时区换算的结果、`alt` 是同一戳按 UTC 的解释、`now` 是设备此刻（必须与行首时间戳一致），
  `TZ` / `LDP` 是换算时的环境（时区与库路径变量）；行尾并排响应头，`now=` 与 `Date` 因此同处一行。
  缺 `signTime` 的记录（例如已请假）两个换算位都留空——不拿 1970 年零点换算出的 `00:00` 充数。
  ```
  时间核对: signTime=[1790938800000] → sign_time=[19:00] now=[2026-10-02 19:30:00] TZ=[未设] LDP=[未设] alt=[11:00] 记录={"records":[{"id":88123,"name":"晚查寝签到","beginTime":1790940000000,"supplementEndTime":1790946000000,"endTime":1790943600000,"signInStudent":{"signState":1},"lng":119.243462,"lat":26.088417,"signTime":1790938800000}]} hdr={Date: Mon, 13 Oct 2025 21:30:00 GMT|Content-Length: 53|Content-Type: application/json;charset=UTF-8|Server: nginx}
  ```
- **`记录len=` + `记录trunc=`**：`记录=` 与 api 层的 `body=` 走**同一个实现**、同一套口径——
  超过 2KB 才截断，并在同一行里标明**原始字节数**与被我们截断（不标的话事后会把「截断」
  读成「服务端只回了这么多」）；不超限时两个字段都不出现。
  ```
  时间核对: signTime=[…] → sign_time=[…] … alt=[…] 记录={"records":[{"id":88123,… 记录len=2650 记录trunc=1 hdr={…}
  ```
  （这条来自 `tests/signin-submit.sh` 的「记录超限」那一档；记录段本身按上限 2048 字节截断。）
- **保活失败行**（`保活: ❌/⚠️ … 调用失败 …`）：`rc=` 是 keepalive 观察到的返回码、`screen=`
  是当时的屏幕状态，随后原样接上 api 层那一行事实，末尾是所采取的动作——判断「网络不通」
  （`net rc=` + 工具原话）还是「登录态失效」（`rc=0` 且服务端给了状态码与正文但没有任务列表）。
  保活**成功**在调试档下仍只有一行心跳（成功是常态，默认档不再逐次记它）；节流未到期那一轮
  **不写**任何保活行，两档皆然。失败行是**两档都写**的那一类（默认档当日只留首次、原因变了再留一条），
  因为失败会影响登录态。
  ```
  保活: ❌ 2_DEAD 调用失败 rc=0 screen=on http=200 body={"code":1,"message":"not login"} 耗时=12ms (今日 0 成功 / 2 失败) — 屏幕亮着，延后（熄屏或签到时段自动刷新）
  ```
  （同样是调试档的产物：默认档下同一行是 `保活: ❌ 2_****a1b2 调用失败 …`。）
- **通知发送失败行**：只有**发送失败**才记（成功与「被配置关掉 / 降权不可用」都不记）——
  判断「提醒为什么没到」。`event=` 是业务事件名（调用方没给名字时退化为 tag），`rc=` 是发送
  命令的退出码，`err=` 是它的输出原文（什么都没吐时写 `(无输出)`）。失败不落「当日已发」标记，
  所以下一次仍会再试。
  ```
  通知发送失败: event=failtask rc=1 err=su: permission denied
  ```

**取舍准则：这一行能否区分两个假设。** 因此失败与状态变化记得详细，而纯重复的正常轮询
（每分钟一条「不在签到时段」、每 15 分钟一条保活心跳）归调试档——它们分不开任何两个假设，
只是同一份事实的重放。同理，保活成功、通知成功、节流未到期都不新增日志行；
**节流未到期那一轮仍然一行都不写**，两档皆然。

**token 的可见度**（唯一一处与档位有关的「写什么」，而不是「写不写」）：
`DEBUG=0` 时全部打印点输出 `2_****a1b2` 形状——**先扣掉 `2_` 前缀（有才留它）**，
再从**扣掉前缀之后的正文**里保留**尾 4 位**；扣掉前缀后恰好 4 位时留下的就是它自己
（例如 `2_ABCD` → `2_****ABCD`），不足 4 位则**整串打码成 `****`**（连前缀一起隐身）；
`DEBUG=1` 时输出明文。**本节上面那些例子里带 `2_…` 的行都是默认档的形状**；
调试档下同一行是明文（`2_C0DE` 这种），**文案与字段一字不差**，只有 token 那一格不同。
保留尾 4 位是为了**仍看得出「换没换」**——打码前后不一致就是刷新成功过，
不开调试也能确认这件事。授权头本来就不落日志（响应头白名单不含它），所以默认档没有别的暗路。
**保活统计文件 `fafu_keepalive.status` 里那份 token 是明文且保持不动**——它是运行时状态、
被当值取用，打码会直接写坏统计（见 §2.3）。因此「默认档 = 日志可安全外发」这句话只覆盖
`fafu_checkin.log` 与 `status` 的输出，**不覆盖整个模块目录**。

**日志轮转参数未变**：仍是超过 256KB 保留最近 1000 行，两档共用同一套参数、不引入调试档专用上限
（长期开着调试档靠既有轮转兜底，不会无限增长），调试期想清空仍靠**每天重刷模块**。

**能力边界（如实标注，别读成服务端的行为）**：

- 设备上**没有可用的 curl**、走 busybox wget 兜底路径时，状态码与 `hdr={…}` 来自
  `wget -S`（它把服务端响应也写到 stderr）：工具吐了状态行就有 `http=` 与白名单四项，
  与 curl 那一档同形。**工具没吐响应时**（连不上，或该 busybox 构建不吐）才没有 `hdr=`、
  `http=` 写 `-`——这是工具的能力边界，不是「服务端没给」，两者在日志里长得不一样正是为了区分。
- wget 兜底路径的 `body=`：4xx/5xx 时 busybox wget **丢掉正文**，那一档因此会出现一个空的
  `body=` 紧跟工具原话（`err=wget: server returned error: …`）——「服务端回了空正文」与
  「工具没把正文给我们」要看 `err=` 才分得清。
- **token 显示成 `2_****a1b2` 不是「取不到 token」**：那是默认档的打码形状（见上面的
  「token 的可见度」）。想知道明文就打开调试档；想知道换没换，看尾 4 位。
  接口调用与签名用的始终是原值，打码只影响显示。

> 本节引用的每一行都是测试夹具跑出的真实产物，想自己复现同样几行：
> `sh tools/run-tests.sh '六类排障日志'`（端到端，完整日志落在
> `tests/.work-run/poll.sh/poll-e2e-logs/mod/fafu_checkin.log`）与 `sh tools/run-tests.sh '保活失败行'`
> （保活两档，落在 `tests/.work-run/keepalive.sh/keepalive-failline/mod/fafu_checkin.log`）。
> 工作根是「一个用例文件一份」（`tests/.work-run/<用例文件名>/`），故路径里那一层是文件名。

## 四、重新逆向指南（当签到失效且疑似接口变更时）

按顺序执行，每步有验证点：

1. **下载 H5 资源**：从 `http://stuhealth.fafu.edu.cn/declarew/` 的 index.html
   提取 `check/js/*.js` 清单并下载（含 `app.*.js`、`chunk-vendors.*.js`）。
   验证：`app.*.js` 中能搜到 `spliceoken`。
2. **定位签名逻辑**：搜索 `spliceoken` / `hashStr` / `Authorization`。
   验证：找到 `md5(SECRET+url+ts+nonce)` 形态的表达式。
3. **解混淆**（jsjiami.com.v7）：字符串表 + RC4 解密器；注意**运行时数组会先被
   轮转**（自校验循环），静态数组需还原后使用。参考实现与适配步骤见 [`tools/re-analysis/`](../tools/re-analysis/)。
   验证：解出的 `hashStr` 指向标准 MD5、密钥为 32 位可见字符串。
4. **验证签名**：用**登录接口**（空 token 签名）测试——
   若返回业务错误（如"authorization code does not exist"）而非 401，签名正确。
5. **更新脚本**：同步 `SECRET` / 接口路径 / 时间字段解析。

> 判定"是 token 问题还是接口变更"：先 `keepalive` 手动测 token；
> token 有效但接口报错 → 才需要走本流程。

### 5.1 本地（不需要手机 / root / 网络）


  `busybox.exe`，CI 是 aarch64 ELF；设备那份还带 Android 内核 / SELinux 差异），
  所以代码里**不得依赖 busybox 的可选特性**：`%N` 未编译时 `date +%s%3N` 会把 `%3N`
  原样吐出，耗时因此以 `/proc/uptime` 兜底（见 §3.5「耗时」）。
  **也不要拿 applet 去解析结构化文本**：设备那份 busybox 的 `grep -oE` 与 `sed` 在
  若干模式上会直接段错误（exit 139）——`json_first` 曾用交替组 `("[^"]*"|[^,}]*)`
  取任务名，在设备上恒为空串，本机却全绿；`_api_hdrs` 曾用 `sed -n 's/.*\(hdr={[^}]*}\).*/\1/p'`
  取响应头段，在设备上同样崩。两处都已改成**纯参数展开**（`case` 判存在 + `${1#…}` / `${1%%…}` 裁剪）。
  经验：能在 shell 里裁剪的，就别 fork 一个 applet；这类缺陷只会在 CI（与设备同构建）暴露。
  参数展开里的**模式写法也只有一种形状能用**：取「带引号键」的值要写成
  `${1##*"\"$2\":"}` 这种「引号在里面、外面再包一层引号」的形式（与 `json_first` 一致）；
  写成裸的 `${1##*\"$2\":}` 时，这份 busybox 的 ash 直接报 `unterminated quoted string`
  （本机 Windows busybox 1.38 同样报，Ubuntu 的 dash 不报——两个环境都会踩，别只在一个里试）。
  同理 `case` 的模式里要匹配引号也得写 `*"\"$2\":"*`。**照抄一处既有形状**比自创写法省事。
  **不要用 `date -d @<epoch>` 算钟点**：设备上这条路给的值是错的（那份 busybox 与系统
  `date` 错法一样）。2026-10-13 的设备探针：`date -d @1791811959 +%H:%M` 给 `17:09`

  这一步。改法是纯算术（`base.ms_to_hm`：当日第几秒 = (戳秒 + 偏移秒) mod 86400），
  只用戳本身与本机偏移这两个已经验过是对的输入，不依赖时区库、也不 fork。

- **Windows + busybox 的四个坑**（本机专属，CI 的 Linux 上不存在）：
  ① 写驱动脚本不能 `cat > "$name.sh"` 之后再追加前导——驱动主体是从 stdin 读进来的，
  那个 heredoc 会变成脚本进程的 stdin，写出来顺序正好颠倒；先落临时文件再拼接；
  ② PATH 上的包装脚本第一行必须是 `#!<busybox> sh`（本机扩展名缺失时只认这种 shebang），
  解释器会把一个多余的 `sh` 留在参数最前面，替身要认；
  ③ `su` 是 busybox 的**内建 applet**，PATH 上的同名文件拦不到它——探测改成显式走 `SU_BIN`；
  ④ 工作目录路径里带空格时，`$变量` 当命令名会因词分割执行失败——顶掉命令要用同名**函数**
  （`nt_send` / `http_post`），不要用「把变量指向函数名」的写法；
- **被 shell 与断言咬过的两处写法**（改代码/改断言时尽量避开）：
  ① 驱动前导用**不带引号**的 heredoc 拼接时，`$( )` 与 `${ }` 会在**写入时**就被展开，
  生成出来的脚本里只剩空串——不是报错，是静默变成另一段程序。要留给运行时展开就写 `\$`
  （前导在 `tests/_signin-common.sh`，同一条口径在 `tests/keepalive.sh` 也用过）；
  ② 分层时**删掉的那个东西往往正是活性所在**：签到提交的成败判据原先写作
  `[ $rc -eq 0 ] && ! echo "$resp" | grep -q '"timestamp"'`，按注释应当「没有 timestamp 才算成功」，
  但实测该式在 busybox 1.35 上把两档判反了（无 timestamp 的响应被判成失败、带 timestamp 的
  被判成成功）。**正解落在 `lib/signin.sh` 的 `_sg_submit_ok`**（改用 `case`），
  这类判据一旦拆进新函数，就会被新写下的断言原样固化下来——所以断言必须与
  **注释声明的语义**对齐，而不是与旧实现的输出对齐；否则旧 bug 会跟着注释一起被"验证通过"。
- 驱动脚本里的路径**一律用相对路径**（`cd` 进临时目录再以 `./x.sh` 运行）：
  Windows 的 `D:/...` 在 sh 里既没有根目录也会被当成分隔符，喂进被测代码会得到 `/mod/...`
  这类残缺路径（踩过）；被测代码在设备上用的仍是绝对路径，这里只是替身环境；
  驱动本体需要的绝对路径（如 `SU_BIN`、`T_WORK`）由前导写好——**别在驱动里读 `$PWD`**；
- 每个驱动一份独立的工作目录（`tests/.work-run/notify.sh/notify-<驱动名>/`）：同一条用例里的多个驱动
  共用目录时，后一个驱动会覆盖前一个留下的产物，断言会静默空转（踩过）；
- 按关键字筛选用例时，含非 ASCII 的关键字在 Windows 控制台上会因代码页被改写，
  优先用 `^api` / `^commands` / `^device` / `^headers` / `^keepalive` / `^layer` / `^notify` /
  `^skeleton` / `^state` / `^desc` 这类纯 ASCII 前缀。

- `tests/headers.sh`：注释口径守卫，两条口径——① 检查入口 + `lib/` + `tools/` + `tests/` 下的 `.sh`

  几处判据细节值得知道：行数按「跳过 shebang 与块前空行、也认缩进注释」数；**空行切断块**，
  于是拆块是合法的减压手段；**文件头豁免只给它自己**（前两行内开始的那个块，即首行或 shebang
  之后那块），以代码开头的文件没有头块、第一个块照常受管，头块之后的每个块（哪怕与它隔着空行）
  也照常受管；分区标题（`# ---- … ----`）算导航，既不自成一块也不算进后面的块；
  行尾短注（贴在代码行后的 `#`）不计入块长、也不设上限；页面按 `/* … */` 与 `//` 计
  （行首与**行尾**的 `//` 都算，免得换个写法绕过去），且页面没有文件头豁免。
  字样一律按**字节**做字面量匹配（中文在 `LC_ALL=C` 下才匹配得上，
  本机与 CI 才会给同一结果）。
  **守卫管不了什么**：它只认机械形状，不判断注释内容是否属实；历史叙事那一条只覆盖词表里
  那几个字样，**带日期的探针叙述它管不住**（本轮实测确认代码里仍有五处：`lib/` 一处、
  `tests/` 四处——日期从来不是判据的一部分，词表里也没有日期）；换成词表外的说法同样能绕过。
  守卫自己不在被检查之列——它的判据里就必须写出那几类字样，`HD_FILES` / `HD_BODY` / `HD_EXEMPT`
  因此留了可覆盖清单的口子。每条扫描断言都先确认「被扫描的脚本数不为零」（清单落空时的零命中是假绿），
  反向样本自证判据不是摆设：一份 16 行头部的临时样本必须被数出超限（块前加空行的等价写法也一样）、
  一份写着「踩过」与 README 的样本必须被全量扫描命中、干净样本必须零命中；本体侧另有
  4 行缩进块、块前空行、行尾短注、分区标题、页面块注释与词表命中的反向样本，
  以及豁免清单本身的自证（空清单时必须一个不漏地全量受管，非空时它真的还会豁免）；

  `key: 'DEBUG', field: 'debug'` 那张表）钉的是「控件在不在、两张表对不对得上」，
  **值本身由 `tests/commands.sh` 在真入口上断言**——页面不自带默认值。
  **视觉口径只有两条被机械守住**：零外部引用（`build.sh` + `ext_url_hits`，
  另有反向样本自证）与「开关仍是 `.sw` 那种 checkbox 形状」（上面那三条接线断言的前提）。
  配色、圆角、字号、行高**没有回归测试**——改 CSS 后要按 §5.5 在 412×915 下出浅色 / 深色截图
  看一眼，机械断言在这里给不了保障。

**写含中文的日志断言时注意**：本机（Windows + zh_CN.UTF-8）的 busybox `grep` 匹配不上
多字节字符，`grep 中文` 恒为 0 处（实测）。`tests/keepalive.sh` 因此把这类断言拆成两步：
用 `LC_ALL=C grep -aF` 取**纯 ASCII 片段**数行数，再把日志窗口抓成小文件后用 `t_has`
逐字比对中文文案（`ka_log` / `ka_near`）。同理，`grep -E` 的字符类要用 `[[:space:]]`
并先 `set -f`——`[ \t]` 在这条链路上会退化成「空格或字母 t」，转义括号会直接报 bad regex。

**日志分级的主缝**（六个跑真入口 + 夹具配置文件的套件，见下面的「十六个套件」）：

- 这六个套件各自的**前导统一把 `DEBUG=1` 写进夹具的配置文件**：`tests/commands.sh`（`cd_setup`）、
  `tests/config.sh`（`cf_setup`）、`tests/keepalive.sh`（`ka_th_setup`）、`tests/notify.sh`（`nt_setup`）、
  `tests/poll.sh`（`poll_config()` 一个出口覆盖全部用例）、`tests/skeleton.sh`（`sk_setup`）。
  于是既有那约 140 条依赖日志文案的断言语义不变——它们测的本来就是**完整行为**（调试档 = 全量现场）。
- **写入位置必须在配置默认值代入之后**，否则会被默认值覆盖。这些夹具都是「先落文件、再由入口
  `cfg_load` 覆盖生效值」，所以直接写进夹具文件即可；**不要**写成加载之后再改。
- **主缝 = 既有的真入口端到端缝**（`tests/poll.sh` 的那条八轮时间线）：**同一条时间线跑两遍**，
  一遍默认档、一遍调试档，断言①默认档里没有那 7 类行但有签到结果行、同一种失败只留一条且
  原因变化时再留一条，②调试档里上述行全部出现，③**两档的文案逐字一致**（把两遍的日志并排比），
  ④默认档下 token 是打码形状、调试档下是明文。它是唯一能同时控制配置文件与时间线、
  并读到整份日志的地方，所以这四条都钉在这里。
- **两处精确计数断言的复核结论**（在「六个夹具 + #26 的失败去重」都落地之后逐条核过）：
  ① `tests/keepalive.sh` 的「整段恰好两行保活日志」**仍然恰好两行**：那条真实入口时间线里
  保活是成功的（心跳行在调试档可见），失败去重那一条用例走的是另一条时间线、不掺进来；
  ② 只读命令前后「日志逐字节相同」**在两种档位下都成立**——只读命令一行都不写，与档位无关，
  故那条断言按两种档位各断言一次（调试档一次、默认档一次），对照的 `notify` 仍必须写下探测行。
  这两处都是「数行数 / 比字节」的断言，**再加档位或再加去重时都要回头确认数的是哪一档、
  哪一条时间线的行**，最容易在这里制造假红/假绿。

### 5.4 设备冒烟（结构改动 / 发版前的真机走查）

```sh
# 设备上以 root 执行（管理器的 WebUI shell，或任一带 root 的终端）
sh /sdcard/Download/device-smoke.sh
# 不想被终端回收打断：nohup 起来，进度会实时写进证据文件
nohup sh /sdcard/Download/device-smoke.sh > /sdcard/Download/fafu-smoke.log 2>&1 &
```

脚本（`tools/device-smoke.sh`，在仓库里，不打进模块）按六节依次跑：第 0 节只动调试档位、
`toggle` 那一项会改开关（第 3 节经 `enable` 恢复成「已启用」），其余全是只读或**无副作用**的往返。
可覆盖的三个变量：`M=<模块目录>`（默认 `/data/adb/modules/fafu-checkin`）、
`OUT=<证据文件落点>`（默认 `/sdcard/Download/fafu-smoke-<时间戳>.txt`，断言里换成临时目录用）、
`WAIT_KA=0`（跳过等保活节拍那一段）。

**冒烟前先打开调试档、退出时恢复**（脚本开头，正文之前）：

- 原档位从 `webstate` 的 `debug=` 字段读（**页面读得到的那一个字段**，不直接读配置文件）；
  读到 `1` 就**一次都不写**（写同样的值是空操作，却会白跑一遍写入闸门）；
  **读不到就不改**（旧版模块没有这个字段，硬塞一个空值会被闸门按「未登记的配置键」拒掉，
  那会把「拿新脚本冒烟旧模块」误判成失败）。
- 打开与恢复都走 `setconfig`（唯一写入闸门），**脚本从不直接改 `fafu_checkin.conf`**；
  恢复挂在 `trap ... EXIT INT TERM HUP` 上，**提前失败（用法报错、中途 bad）也走同一条路**——
  留着调试档开着会让使用者的日志一直涨，而那是脚本造成的。
- 这条前置是必需的：第 1 节的降权探测行与第 5 节的保活心跳在默认档都不写，不先开档，
  脚本会把「这行被收起来了」误判成「链路坏了 / 节拍丢了」。第 2 节那两次 `status` / `webstate`
  也因此读到明文——它们要拿 `status` 里的 token 当原像去比 `webstate` 有没有泄露它，
  **拿打码串去比会永远不命中、那条检查会静默变成空转**（顺序不能调换）。
- **这份脚本的前提是「只对当前版本的模块跑」**（脚本注释里写明）：档位没打开时，
  后面那些依赖调试档的观察点会**静默空转、而不是报红**——最典型的就是上面那条
  「webstate 不吐明文」（拿打码串去比，永远不会命中，于是恒过）。
  所以读不到 `debug=` 时它整段跳过、不猜也不改；**别把「没报红」读成「验过了」**。

六节各做什么：

0. 前置：模块目录与层文件（**数量由入口 `FAFU_LAYERS` 数出来**，不写死；另核对无符号链接、
   权限未被收成 600），并回声本次档位改动（`调试档: 本次冒烟为开（退出时恢复为 X）`）与版本
1. 启动与安装完整性：日志里有启动行、**没有**「模块不完整」/「缺少库层」，且最近一条启动行的
   `notify=[...]` 是实测写法（`notify=[不可用]` 只记提醒，不当失败）；再核最近一条降权探测行
2. 六条手动命令：`status` / `webstate` / `notify` / `once` / `toggle` 五条逐个跑（`toggle` 会改开关）
   外加收尾，逐条记下**时刻 + 退出码 + 完整输出**。`webstate` 那一项核四件事：页面要用的字段齐不齐
   （**含调试档位 `debug=`**；旧版模块缺字段才另说）、**输出里不含凭证明文**（拿第 2 节取到的
   `status` token 原文去比）、以及它**没有白探降权**（探了会往日志里写一行，而它交出的日志尾部
   就是页面的「最近日志」——读一次状态就会让页面第一条变成与本次操作无关的降权行；
   判据是这一趟前后 `通知链路` 行数不变，守护进程自己不探，故这个计数不受它并发写日志的干扰）
3. 恢复启用状态：开关若已被 `toggle` 切走就 `enable` 回来，并核对 `开关: 🟢 已启用` / `守护进程: ✅ 运行中`
4. 动态描述：`status` 的「描述:」行；`ksud` 可读时**以 KernelSU 覆盖值为判定**
   （管理器显示的就是它），`module.prop description` 只作参照（它是安装包固定的静态文案）
5. 保活：先手动保活一次验链路，再等下一个 15 分钟节拍出现新记录（`WAIT_KA` 秒上限，默认 1000，
   可设 `0` 跳过；每 30 秒采样一次）。判定用的保活窗口**向模块的配置层现读**
   （起止都可配，冒烟脚本不另抄一份钟点），**等的是调试档下的心跳行**（见开头）；
   窗口内等满仍无新记录算失败，窗口外等不到只记提醒（那是设计使然）
6. 写入闸门往返：把当前生效值原样交给 `setconfig`（**不改变任何配置值**），断言它接受并回显
   同一套值——「校验先于落盘」这条链因此也在真机上走了一遍。键清单是
   `KEEPALIVE POLL_START POLL_END NOTIFY NOTIFY_LEAD NOTIFY_COOLDOWN KA_START KA_END` 八项
   **外加档位键 `DEBUG`**（它现在是在册键，且此刻生效的就是本次打开的那一档）；
   旧版模块的 `webstate` 里读不到 `debug=` 时**这一项不进清单**（同「读不到就不改」那条理由）

证据边跑边写 `OUT`（默认 `/sdcard/Download/fafu-smoke-<时间戳>.txt`），退出码另走同名 `.rc` 文件
（**攒到最后一次性写盘的话，终端被回收就什么都留不下**——踩过；结论数也走 `.rc`，
因为正文是经 `sh -c` + `tee` 跑的，管道之后 `$?` 是 `tee` 的、拿不到正文的退出码）。
**通知是否真的到达仍需目视确认**（见 §5.3），脚本只能证明「已交给系统发送」。

> 这份脚本的**契约断言**在 `tests/device-smoke.sh`（§5.1）：它只能在真机上跑完，故断言钉的是
> 「在本机就能观察到的那两件事」——冒烟前经 `setconfig` 打开调试档、退出时恢复成进脚本时的样子，
> 用模块桩（把每次子命令调用按顺序记进文件）当观察面；第 6 节的键清单只能用静态锚点守着。

### 5.5 页面视觉走查（改 CSS 之后）

**本机也能看**——不需要手机、不需要 root：页面只依赖 `window.ksu.exec` 一个外部接口，
在桌面浏览器里给它装一个假桥就能把状态填满（`file://` 直接打开只会看到「请在管理器里打开」的横幅，
那不是坏了，是设计如此）。

1. 用 Playwright / 任意浏览器开发者工具，在**页面脚本执行之前**注入 `window.ksu`。
   **假桥的回调是「挂在 window 上的名字」而不是函数**——`ksu.exec(line, opts, cb)` 里的 `cb`
   是字符串，必须写成 `window[cb](0, out, '')`；写成 `cb(0, …)` 会报 `TypeError: cb is not a function`，
   页面于是永远停在「读取中…」（这个坑踩过一次，症状极具迷惑性：布局全对、状态全是「—」）。
2. 视口 **412×915**、`prefers-color-scheme` 分别设 `light` / `dark`，各看一眼；
   **用视口截图而不是整页截图**——`#snack` 是 `position:fixed`，整页拼接时会重复出现，
   看着像「提示没消失」。
3. 要看的四处：首屏运行状态（八项是否都有值，含「守护进程」；把假桥的 `daemon=` 换成 `stopped`
   再看一眼——提示条应出现，改回 `running` 后消失）、配置区的「轮询范围」一行（窄屏下两个输入框
   应一致地折到标题块下方占满一行）、高级区展开、以及一次**被拒绝**的保存（原因必须常驻在
   `#msg` 里、底部提示必须已经收掉）。
4. 数值用计算样式机核：开关的轨道与滑块尺寸、输入框聚焦时的描边宽度与颜色、卡片的圆角/边框/阴影。
   **具体数值只在 §2.1.3 那张表里有一份**，本节不再抄一遍——两处都写就必然漂移。

**只有真机能验的**：滚动手感、系统字体（HyperOS 上 `system-ui` 解析到 MiSans）的实际观感、
刘海安全区（`env(safe-area-inset-*)` 在桌面浏览器恒为 0）、以及管理器 WebView 对
`.75px` 边框与 `env()` 的支持程度。真机走查照 §5.4 的清单走，**页面这一项看四件事**：
① 打开即见运行状态且无横向滚动；② 高级区默认折起来、点一下展开；③ 开关点击有位移过渡、
   无闪烁；④ 保存一次合法值（页面上回显新值）与一次非法值（当场拒绝、旧值不变）。

## 六、维护约定

- **发布**：手动流程——CI 只构建（产物见 Actions artifact），Release 由维护者手动创建；
  发布说明以 [CHANGELOG.md](../CHANGELOG.md) 对应小节为唯一来源（发布时从该小节取出）。
  **顺序上有一条硬约束：Release 与它的 zip 资源必须先存在，最后才同步 `update.json`。**
  两个管理器都只按 `update.json` 的 `versionCode` 判定更新（KernelSU：`versionCode <= 已装` 即跳过、
  `zipUrl` 为空也跳过；Magisk：`json.versionCode > 已装` 才置 `outdated`），
  仓库里的 `module.prop` **不会被拉取**、它只决定本地打包的版本串；
  所以 `update.json` 是唯一打开提示的开关，在资源就位前同步它 = 用户点更新拿到 404。
  步骤见 README「发布新版本」
- **更新日志面向使用者，只与上一个已发布版本对比**：逐条问「v<上一版> 的使用者会遇到这个吗」，
  遇不到就不写。据此两条硬判据：
  ① **开发过程中引入、又在本版发布前修掉的缺陷，一个字都不写**——使用者从没遇到过它，
     写进去只会暴露内部流程（这一条最常被写错：拆层、改接口、加子命令时引入的回归都属此类）；
  ② 不写「修复：…」这类内部标签，直接陈述升级后的行为，写的永远是「你会经历什么」。
  其余不进的：重构、断言与测试项数、提交号、内部函数与文件、CI、调试细节、子命令与内部文件清单；
  它们留在本开发文档与提交信息里（改到哪个坑记进第三部分，实现取舍记进 §2.1.2 的层内实现注记）
- **版本号**：手动维护（`module.prop` 的 `version` / `versionCode`），不自动递增。
  **开发构建在包内把 `version` 写成 `<版本>-dev.<短 SHA>`**（`build.sh dev`，语义化版本的连接号必需），
  故装机后从 `status`、启动日志、模块列表或配置页都能分辨装的是哪一次构建；
  发布构建的版本串与 `module.prop` 逐字一致，`versionCode` 两者都不动
  （它决定更新检测看不看得见这一版；`update.json` 在发版前故意停在已发布的那一版）
- **发布 tag 一律带注释**（`git tag -a`）：注释存的是发布标题，v1.0.0 起的每个版本都这样。
  两个走过的坑：① `gh release create --verify-tag=false` 会**顺手建轻量 tag**，
  破坏这个约定（v1.3.0 首次发布时踩到，只能删掉 tag 重建）；② **删远端 tag 会让 Release 变成 draft**
  ——更新源仍在、但管理器看不到更新，故重建 tag 后必须 `gh release edit <tag> --draft=false`
  把它发布回来（v1.3.0 修复时踩到）。命令与顺序见 README「发布新版本」
- **文案**：日期用绝对形式（如 `09-14`），不用「今日」等相对表述——守护进程退出后信息不失真
- **代码**：一次性 / 临时的逻辑不入代码，在会话中给出命令即可
- **注释**：口径见 §2.1 的层结构约定（第二版），论证与依据写进 §2.1.2 的「层内实现注记」，
  代码里只留结论；改完用 `tests/headers.sh`（`sh tools/run-tests.sh ^headers`）自查
- **文档**：只写读者需要的内容（事实 / 约定 / 方法），不记录会话过程与已取消的方案；
  现状描述以代码为准，变更记录的历史条目按当时的实际经过保留
